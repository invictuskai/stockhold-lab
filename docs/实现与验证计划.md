## 2. 关键类职责

### ReservationFacade

- 不持有事务。
- 规范化请求、校验边界、计算幂等 hash。
- 调用一次 reserve 事务。
- 事务结束后经 RefillSingleFlight 补充不足维度，按补充结果决定立即重试或抖动重试。
- 控制总尝试次数、退避、错误映射与业务指标。
- 数据库不可用 / 连接获取超时不重试，交给熔断器计数。

### RefillSingleFlight

- 按 InventoryKey 合并同一实例内的并发补充；等待方在 Future 上等待（上限 500ms），不持有连接。
- 结果携带 potentialAvailable 与完成时间，等待方按自身需求量判断 INSUFFICIENT / ALREADY_REFILLED。
- 发起方异常时所有等待方收到同一异常分类，不静默吞掉。
- Map 条目在完成后立即移除，防止内存泄漏；有单元测试覆盖。

### ClaimService

- 普通 claim、ACTIVE 上的 lateClaim、EXPIRED 上的 lateClaim（重新取得额度）三条路径。
- 使用 critical 舱壁与更长的重试预算。
- 条件更新影响 0 行时抛出不变量异常，由上层在独立事务中冻结维度。

### resilience 包

- AdmissionController：降级等级、全局许可、热点维度许可、冻结缓存的统一入口；拒绝不获取连接。
- HotKeyLimiter：每实例每 InventoryKey 的并发许可，条目 LRU 淘汰，数量有上限。
- ReserveCircuitBreaker：只统计数据库类错误，只作用于 reserve。
- DegradeModeRegistry：L0~L3 状态、切换事件与原因，通过 Actuator 暴露。
- SqlErrorClassifier：把 MySQL 错误码 / SQLSTATE 映射到总体方案 10.2 的错误分类，是所有重试决策的唯一来源。

### ReservationTransactionService

- 每个方法代表一个完整短事务：tryReserve、claim、cancel。
- 显式选择 RC。
- 按协议控制 SQL 顺序与更新行数。
- 不在事务内调用远程服务、不休眠、不循环等待库存池。

### PoolRefillService

- refillOneDimension：锁一个账本、统计池、计算可发放额度、原子批量插入。
- 返回补充数量和可用量判断结果，但不承诺后续请求一定领取成功。
- 不把 Hikari pending 高错误解释为库存不足。

### Repository

- 使用 JdbcTemplate / NamedParameterJdbcTemplate。
- SQL 显式附带固定 conn_tag。
- 单位删除按维度和确切 ID；断言受影响行数。
- 时间、UUID 二进制编解码、Long 精确运算有独立测试。

### ConnectionAttributionDataSource

- 获取连接前记录获取等待。
- 获取成功后记录直到逻辑连接 close 的持有时间。
- 从业务操作上下文读取固定枚举标签，在连接获取时固定归因。
- 异常、事务回滚、线程复用后正确清理上下文，避免标签串线。
- Hikari 默认指标之外的连接持有时间需要自行实现，不能假设自带按业务归因。

## 3. 开发里程碑

### M0：评审设计（当前阶段）

交付：总体方案、DDL、API、事务协议、数量边界、测试和压测计划。

确认以下取舍再进入实现：

- Java21 + MySQL8.4。
- `allocated_quantity` 用于安全发放额度。
- 取消 / 超时先回账本额度，不直接返还单位行。
- 第一版整单最多1000单位、单维度不超过池容量。
- 不对外部支付承诺原子性；以宽限期 + lateClaim 最大化兑现，失败暴露为补偿点。
- 服务端 fail-closed；少卖优于超卖；过载时先舍新 reserve、保 claim。

### M1：最小可启动仓库

- Maven Wrapper、Spring Boot、JDBC、Flyway、Compose、测试依赖。
- 初始化 / 调整 / 查询库存 API。
- Testcontainers 执行真实 DDL；修正任何 MySQL 语法问题。
- 所有配置使用 UTF-8、UTC，支持 Windows PowerShell 和 Bash。

验收：干净环境可启动；迁移成功；健康检查可用；配置不含真实凭据。

### M2：最小正确性闭环

- refill、reserve、claim（含宽限与两种 lateClaim）、cancel。
- 默认逐维度 SELECT；先不引入 UNION ALL。
- 实现幂等唯一键冲突处理与全事务回滚。
- SqlErrorClassifier 与三个连接池舱壁。
- 冻结 / 解冻、reclaimPool 调整。
- 单线程状态机、不变量检查与 API 合约测试。

验收：H/A/P/R 的每一步变化可验证；重复请求不会重复预留或扣减；每条错误路径返回契约中的错误码。

### M3：并发、过期与健壮性

- 多维度排序锁、并发争抢、同步补充、single-flight、有界重试。
- 到期清理（自适应批量、毒丸隔离）、多实例重复扫描、热点主动补充。
- 准入控制、热点限流、熔断、降级等级。
- 秒杀适配：BATCHED 结算与结算任务、每买家限购、售罄快速拒绝、开售预热、可用量缓存。
- 故障注入（含 Toxiproxy）、死锁 / 锁等待处理、提交结果不明路径。

验收：第 4 节所有并发、故障与健壮性测试通过，不变量零违例；[极端场景与降级预案](极端场景与降级预案.md) 中每个标注“验证”的场景都有对应的自动化测试或实验记录。

### M4：可观测性与性能实验

- 业务标签、连接获取 / 持有 / 事务耗时指标，按舱壁拆分。
- k6、单计数器对照方案、池大小矩阵、长事务注入实验。
- 复现文章结论的对照实验：自增主键 vs 复合主键锁数量、innodb_thread_concurrency 调参。
- 编排策略对照：补充后立即重试 vs 固定抖动、single-flight 开关、随机起点开关。
- 降级演练：洪峰下自动进入 L2 并阶梯恢复，claim 成功率不受影响。
- 可选 UNION ALL 路径，先通过相同正确性测试再比较性能。

验收：报告包含环境、配置、命令、原始指标与正确性校验，不能只有 QPS 截图。

ProxySQL 归因实验、Redis 影子迁移模拟、大单专用路径、在线池容量调整、数据归档。均不阻塞核心复现。

## 4. 集成与并发测试矩阵

所有锁相关测试用真实 MySQL8.4，禁止用内存数据库替代。并发测试使用多个连接及 Barrier / Latch 精确构造交错，不以长时间 sleep 猜测发生顺序。

### 4.1 基础生命周期

| 场景 | 核心断言 |
| --- | --- |
| H=10初始化再refill | H=10,A=10,P=10,R=0 |
| reserve3 | H=10,A=10,P=7,R=3 |
| claim3 | H=7,A=7,P=7,R=0 |
| cancel3（独立数据） | H=10,A=7,P=7,R=0,F=3 |
| 再次refill | 回收的F再次进入池，不增加H |
| H=0请求预留 | 真实库存不足，无残留头 / 明细 |
| ACTIVE已过期未清理 | claim失败，额度仍占用直到expiry提交 |

### 4.2 核心争抢

1. **最后一件**：H=1，100个不同key并发reserve1，最终只存在一个成功 ACTIVE 预留；其余正确区分不足或临时繁忙，不超卖。
2. **大库存穿透池容量**：H=10000、C=1000，累计创建超过1000个未确认预留；R可超过1000，P始终<=1000。
3. **热点整单数量**：H=1000，多线程每次reserve3，成功数量不超过333；剩余1不会被虚构成3。
4. **分区隔离**：分区A售罄不能消费分区B或默认分区，除非请求显式指定。
5. **多商品原子性**：A足量、B不足，返回失败后A的单位没有丢失。
6. **输入顺序相反**：并发请求[A,B]和[B,A]，规范化后使用一致访问顺序。
7. **跨商家隔离**：相同item/partition和相同幂等键，在不同商家（shop_id）之间相互独立。

### 4.3 补充竞态

1. P=0且F>0，100个请求同时refill；P<=C，A增量等于新增单位数，不重复发放。
2. 一连接锁住全部池单位但不提交，另一连接reserve：不能报售罄；竞争解除后可成功或先返回BUSY。
3. 上述锁定事务分别执行commit和rollback，验证两种可见性路径。
4. refill读完COUNT后暂停，其他reserve提交消耗，再继续补充：只会少填，不超过C。
5. 并发refill与claim / cancel / expiry：账本行锁串行化额度变化，A=P+R恒成立。
6. 库存已全部发放为ACTIVE预留，P=0,F=0：正确报告真实不足，不无限补充。
7. 请求超过poolCapacity或整单1000上限：422，无任何库存写入，不进入重试循环。
8. RC空池锁定读与插入补充的实测；RR作为诊断对照，收集锁证据，不把其特定死锁作为所有版本必现行为。
9. 同实例100个请求同时触发同一维度补充：single-flight 下只产生1个补充事务，等待期间补充相关连接占用 <= 1；等待者按自身需求量得出正确结论。
10. single-flight 发起者补充失败：所有等待者收到同一错误分类，Map 条目被清理。
11. 补充成功后立即重试：断言该路径无睡眠，连续立即重试次数不超过上限。
12. 固定 ID 生成器制造单位 ID 碰撞：补充整体回滚并以新 ID 重试成功，A 只增加一次。
13. 冻结维度补充：无插入、A 不变、返回 FROZEN。

### 4.4 幂等与状态竞争

1. 相同幂等键并发100次相同请求：仅一个预留，其他返回同一ID或可重试错误，最终重试收敛。
2. 相同key不同请求：409，不产生第二份预留。
3. JSON行顺序变化、重复行合并、默认TTL显式化：规范化hash一致。
4. 相同paymentReference重复claim：仅扣减一次。
5. 不同预留抢相同paymentReference：最多一个成功，另一事务扣减全部回滚。
6. claim与cancel竞争：仅一个终态，库存扣减或释放恰好一次。
7. claim与expiry竞争：以头锁保护下的时间检查为准，不允许扣减且释放同时发生。
8. 多个expiry实例扫描同一ID：只释放一次。
9. 已CLAIMED在TTL之后重试claim：正确幂等成功。
10. 超时但尚未清理的ACTIVE重复reserve：返回原预留，不创建新库存占用。
11. expires_at 之后、claim_deadline_at 之前 claim：成功，claim_mode=RESERVED。
12. claim_deadline_at 之后、expiry 之前：普通 claim 返回 409 且 lateClaimAllowed=true；带 lateClaim 成功，claim_mode=LATE，H/A 各减 n，P 不变。
13. EXPIRED 后 lateClaim，分别覆盖：F 足够（P 不变）；F 不足但池足够（P 与 A 同减）；二者都不足（409 LATE_CLAIM_INSUFFICIENT_STOCK，无任何写入）；池单位被在途 reserve 锁住（503，无写入）。
14. lateClaim 与普通 reserve 并发争抢最后几件：不超卖，A=P+R 恒成立。
15. lateClaim 重放（同 paymentReference，带或不带 lateClaim）：只扣减一次。
16. CANCELLED 上 lateClaim：409 INVALID_RESERVATION_STATE。
17. 两个实例以不同 grace 配置运行：claim 与 expiry 判定只取决于持久化的 claim_deadline_at。

### 4.5 回滚与故障注入

在以下位置可控抛异常，断言全部回滚：

- 删除池单位后、插入预留明细前。
- 插入部分明细后。
- claim更新部分账本后、更新头状态前。
- refill更新allocated后、插入单位前。
- refill部分批次插入后。
- cancel / expiry更新账本后、更新头前。

其他场景：

- 人工构造死锁，验证1213整事务重试。
- 人工构造锁等待超时，验证1205不会部分提交。
- 提交成功但HTTP响应丢失，原幂等键重试不重复占用。
- 客户端断连不等价于数据库回滚；查询必须反映真实提交结果。
- 应用进程退出后重启，未提交事务回滚，已提交过期预留由job回收。
- 数据库不可用、Hikari超时返回503，不伪装成库存不足。
- Long越界、数量合并溢出、非法UUID与跨shop访问失败。
- lateClaim(EXPIRED) 在删除池单位后、更新头前抛异常：全部回滚。
- reclaimPool 调整在删除池单位后、更新账本前抛异常：全部回滚，操作记录不残留。

网络与数据库故障（Testcontainers + Toxiproxy）：

- COMMIT 阶段断连：reserve 用同一幂等键重试后只有一份预留；claim 重试只扣减一次。
- 延迟 / 黑洞毒性：语句超时与 socketTimeout 生效，线程不无限挂起，返回 503。
- 断开后恢复：熔断打开 → 半开 → 关闭；恢复期间 reserve 按阶梯放开。
- 模拟只读错误（1290 / 1836）：映射为 503 DATABASE_UNAVAILABLE，不重试。
- 条件更新影响 0 行（手工篡改账本）：claim 回滚、维度被冻结、返回 500。

### 4.6 健壮性与降级测试

对应 [极端场景与降级预案](极端场景与降级预案.md) 的场景编号：

1. **舱壁隔离（T2）**：reserve 舱壁被打满、后台任务被人为拖慢时，claim 的成功率与 P99 不受显著影响。
2. **热点隔离（T1）**：单一热点维度洪峰时，热点返回 429 INVENTORY_THROTTLED，其他维度的成功率不下降。
3. **准入不占连接**：429 / 熔断拒绝的请求不获取数据库连接（连接获取计数不增长）。
4. **降级等级（第 3 节）**：L1 关闭快照 / 审计与实验开关；L2 拒绝 reserve 但 claim / cancel / expiry 正常；L3 所有写接口 503；恢复时阶梯放开。
5. **冻结（C1、C4）**：冻结后约 1 秒内新 reserve 被拒绝；缓存陈旧窗口内的 reserve 不会导致超发；claim / cancel / expiry 仍可执行；解冻前审计失败返回 409。
6. **过期积压（L7、L8）**：停止过期任务积累 1 万条逾期预留后恢复，自适应批量生效、每条只释放一次；注入毒丸记录不阻塞其他记录。
7. **reclaimPool（P7）**：池内足够、缺口被 ACTIVE 占用、池单位被锁住三种情况分别返回 200 / 409 / 503，ACTIVE 预留不受影响。
8. **UNION ALL 自动关闭（D9）**：注入异常结果后当前请求走逐维度路径成功，开关被关闭并告警。
9. **优雅停机（A3）**：停机期间在途请求完成或明确失败，无半提交。
10. **长事务影响（D7、P8）**：注入持续打开的长事务，观察 history list 与 reserve 延迟的变化，并验证告警触发。

### 4.7 秒杀专项测试（移植自 verification/）

1. 锁行为：复合主键每单位 1 个记录锁；RR 空池间隙锁阻塞补充、RC 不阻塞；RC COUNT 看得到未提交删除；UNION ALL 分支独立 SKIP LOCKED。
2. CHECK 约束正反例，包括可空列（claim_mode、expired_at）的 NULL 情况。
3. 秒杀全流程（BATCHED 与 SYNC 各一次）：限购、幂等重放、确认 / 重复确认、取消、超时、迟到确认（ACTIVE 与 EXPIRED）、热点补充、过期扫描、结算并发运行，结束后审计：不变量、不超卖、无人超限、额度表与明细一致、无残留分录、只出现预期内的结果码。
4. BATCHED 与 SYNC 在活动中途切换，审计仍然成立。
5. 结算任务停掉时，refill 内联结算仍能回收释放的额度。
6. 售罄缓存：缓存期内回流的库存最多晚一个 TTL 可售；不会因此放行超卖。
7. 同一买家并发 / 换幂等键下单不突破限购；lateClaim(EXPIRED) 超限时返回 BUYER_LIMIT_EXCEEDED。
8. 逻辑库存分区（移植自 partitions.js 与 partition-edges.js）：同一 SKU 多分区并发销售；在途划拨；关闭后拒绝预留 / 补充 / 划入；退回等待 ACTIVE 清零、单位被锁时 BUSY；划拨需回收池单位、被 ACTIVE 挡住、幂等重放；退回后迟到确认；三种范围的限购叠加；规则中途改值 / 停用 / 新增后额度原路退回；每维度与 SKU 合计审计。

### 4.8 随机状态机测试

随机执行补货、减库存（含 reclaimPool）、reserve、claim、lateClaim、cancel、推进到期、refill、冻结 / 解冻；保存随机种子。单线程用内存参考模型对照；并发阶段在静止检查点核对全量不变量与审计总量。

失败输出：种子、操作日志、事务错误、库存快照和必要的数据库锁证据。不得通过清空数据或延长等待掩盖错误。

## 5. 后台任务初始策略

### PoolRefillJob

- 每1秒 keyset 分页扫描库存维度，使用普通COUNT筛选池低于25%且F>0的维度。
- 每个维度独立事务填充到capacity；最多2个并发补充worker；使用 background 舱壁。
- 多实例第一版允许重复探测，但实际补充由账本锁串行化；加随机调度抖动。
- 此扫描是实验方案，库存维度巨大时不可直接扩展为每秒全表扫描；后续改成候选队列或分片调度。
- 正确性不依赖job及时执行，reserve不足时有同步路径。
- 跳过冻结维度。L1 及以上等级暂停，只保留热点补充。

### HotKeyRefiller

- 10秒内触发同步补充 >= 3 次的维度进入热点集；每实例最多200个，60秒无触发移出。
- 每100ms对热点做普通COUNT，低于50%且F>0时补充；与 PoolRefillJob 共用 background 舱壁和 worker 上限。
- 热点集满时淘汰最久未触发的条目，不无界增长。

### ReservationExpiryJob

- 基线每1秒扫描最多200个候选（`claim_deadline_at <= now`）、2个worker，每条独立释放事务。
- 最老逾期超过30秒时提升到每秒1000个、4个worker；积压消除后回落。
- 可多实例运行，重复候选无害。
- 不向连接池一次提交无界任务。
- 同一记录连续失败3次进入隔离表，指数退避，并冻结相关维度、告警；游标越过继续。
- 监控最老未释放到期时间，不仅观察job有没有报错。
- L3 WRITE_FREEZE 时暂停（少卖）。

## 6. 压测方案

### 6.1 对照组

单计数器模式放在独立benchmark profile / 独立表中：预留时原子条件更新同一个维度的available计数，并在同一事务维护预留记录。

必须与单位池模式保持等价的幂等、状态机、失败语义和读写持久性。不能拿“裸UPDATE”对比包含完整幂等和审计的预留接口，也不能在相同数据上混用两种模式。

### 6.2 负载维度

| 维度 | 候选值 |
| --- | --- |
| 商品分布 | 单一热点；10热点；1000商品均匀；倾斜分布 |
| 并发请求 | 1、10、50、100、200，按硬件上限停止 |
| 池容量 | 50、100、500、1000 |
| 单次单维度数量 | 1、5、50，不超过当前容量 |
| 购物车维度数 | 1、5、20，整单<=1000 |
| Hikari最大连接 | 8、16、32、64，记录MySQL连接限制 |
| API负载 | reserve-only短窗；完整生命周期 |
| SQL模式 | 逐维度SELECT；经过验证的UNION ALL |
| 补充编排 | 补充后立即重试 / 固定抖动；single-flight 开 / 关；热点补充开 / 关 |
| 扫描起点 | 固定从头 / 随机起点 |
| 连接舱壁 | 单一连接池 / 三舱壁（同等总连接数） |

完整生命周期负载可使用70%预留后claim、20%预留后cancel、10%等待expiry。TTL缩短必须仍符合契约，并让过期清理有足够时间执行。

reserve-only 必须准备足够库存、限定测量窗口，并记录结束时R；不能因为库存耗尽后请求快速返回409而误称吞吐提升。

### 6.3 制造连接瓶颈

在benchmark profile中增加可控的“获取连接后持有100ms但不执行SQL”的工作负载，以及等长的“事务外等待”对照。

验证：

- 前者使持有时间和Hikari pending明显上升，可能在CPU未满时降低吞吐。
- 后者不持续占用连接。
- 业务归因能够识别注入的调用方，而不是把问题一律归咎于reserve慢SQL。

测试代码不得进入普通dev / production配置，不提供用户可控SQL SLEEP接口。

在同一注入负载下对比单一连接池与三舱壁：舱壁模式下 claim 的成功率与 P99 应保持稳定，reserve 在舱壁内快速失败（429 / 503）而不是拖垮全局。

### 6.4 复现文章结论的对照实验

| 实验 | 做法 | 观察 |
| --- | --- | --- |
| 自增主键 vs 复合主键 | benchmark profile 建一张 `id AUTO_INCREMENT` 主键 + 维度二级索引的单位表，执行相同的 SKIP LOCKED 领取 | `performance_schema.data_locks` 中每领取一个单位的锁记录数（文章：两处变一处）、吞吐与 P99 |
| RR vs RC 空池补充 | 空池上执行 SKIP LOCKED 后并发补充 | gap / supremum 锁与补充阻塞、死锁（诊断用途） |
| innodb_thread_concurrency | 在“CPU 未满但 Threads_running 排队”的负载下调整该参数 | 吞吐、排队、CPU 的变化（文章：保守配置成为隐性瓶颈） |
| 补充编排策略 | 热点洪峰下对比立即重试 / 固定抖动、single-flight 开关 | P50/P99、同步补充次数、补充相关连接占用 |

所有对照实验与主实验使用同一套正确性校验，结束时 H/A/P/R 不变量必须成立。

### 6.5 报告要求

每组预热30秒、测量至少120秒、重复3次；如果设备资源不足，明确降级并记录实际时长。

记录：

- CPU / 内存 / 操作系统 / 容器资源限制。
- JDK、MySQL、应用版本及有效事务隔离级别。
- MySQL innodb_thread_concurrency、max_connections、Hikari配置。
- 成功QPS与尝试QPS分别报告。
- P50/P95/P99、超时、429、503、真实不足比例。
- reserve / claim / refill分别的SQL数、事务数、连接持有时间。
- CPU、Threads_running、锁等待、死锁、补充频率。
- 补充结果分布、claim_mode=LATE 比例、LATE_CLAIM_INSUFFICIENT_STOCK 次数。
- 降级等级变化、熔断事件、429 拒绝原因分布、各舱壁 pending。
- 最终H/A/P/R及不变量检查。

没有固定硬件基线前不设武断QPS验收值；验收重点是正确性、可重复性、指标可解释性。
