# 秒杀场景评审与验证报告

日期：2026-10-01
评审对象：本仓库设计 v1.1，以及据此修订的 v1.2
依据：Shopify Engineering，[We replaced Redis with MySQL for inventory reservations—and it scaled](https://shopify.engineering/scaling-inventory-reservations)（2026-05-12），含文中嵌入的两段 SQL gist
验证方式：在本地 MySQL 8.4.9 上，用按设计协议编写的参考实现做锁行为测试、全流程并发模拟和单 SKU 压测（脚本见 [verification/](../verification/README.md)）

## 1. 结论

**可行，但必须满足第 6 节的上线条件。** 文章的核心机制（每件一行 + SKIP LOCKED、有界池、复合主键、RC、统一锁顺序）在本地实测中全部成立，可以直接用于秒杀的“抢”这一步。但秒杀与文章场景有三点关键差异，原方案 v1.1 若不调整就会出问题。v1.2 已针对它们修订，并通过实测验证：

| 差异 | v1.1 的问题（已实测） | v1.2 的处理 | 修订后实测 |
| --- | --- | --- | --- |
| 流量集中在单个 SKU，确认和超时释放也集中爆发 | claim / 释放同步扣账本，账本行成为新热点：单 SKU claim 约 238 次/秒；模拟中 549~626 次 claim（多轮结果）因排队超过截止时间而失败 | BATCHED 结算：claim / 释放只写分录，批量合并进账本（7.12） | claim 约 1,210 次/秒（约 5 倍），所有 BATCHED 模拟 0 次超时 |
| 绝大多数请求最终都是“售罄” | 每个售罄请求都要访问数据库（reserve 事务 + 判定不足的 refill），并争抢账本锁 | 售罄快速拒绝：缓存 300ms 内的不足判定（15.2） | 5,000 个售罄请求只有 32 个访问数据库，处理能力 7.5~9 万次/秒 |
| 秒杀必须限购 | 原方案没有买家维度 | 每买家限购，与预留在同一事务原子校验（7.13） | 每轮约 3.15 万次请求、1.2 万买家，0 人超限 |

测试还发现并修复了两个缺陷：

1. **reserve 的加锁顺序会导致死锁**：v1.1 先插入预留头，池不足回滚后，同一幂等键的重试会在唯一索引的删除标记记录上加 S 间隙锁，相邻键的重试互相死锁（实测 3 次，InnoDB 死锁日志确认）。改为与文章一致的“先 SKIP LOCKED 领单位、再插入头”后，完整一轮测试 InnoDB 死锁计数器没有增加（4.5）。
2. **DDL 缺陷**：可空列上的 CHECK 约束因 SQL 三值逻辑形同虚设（CLAIMED + claim_mode=NULL 会被接受）。

## 2. 为什么要专门评审秒杀场景

文章解决的是 Shopify 全平台结账时的预留：SKU 非常多，单个 SKU 的并发相对分散，预留发生在“点击完成购买、开始支付”时。秒杀的负载形态不同：

- 一个或少数几个 SKU 在几秒内承受全部流量；
- 库存远小于请求量，95% 以上的请求的正确结果是“售罄”；
- 成功预留后，大量确认（支付成功）和超时释放集中在同一 SKU 上；
- 有限购、开售预热、页面高频轮询余量等需求。

因此逐项复核：文章的每个机制在秒杀下是否仍然成立，以及有哪些文章没有覆盖的瓶颈。

## 3. 逐项对照文章

| 文章机制 | 本方案 | 实测证据 | 秒杀下的结论 |
| --- | --- | --- | --- |
| 每件库存一行，`FOR UPDATE SKIP LOCKED` 领取 | 7.2 | L2：另一事务锁住 3 行时，本事务不等待、拿到其余 7 行 | ✅ 成立，是秒杀“抢”这一步的核心 |
| 每个商品 / 地点的池最多 1,000 行，由补充进程从账本补 | 7.4，`allocated_quantity` 防重复发放 | 模拟与压测中 P 始终 ≤ 1,000；审计 A=P+R 全部成立 | ✅ 成立；库存不超过 1,000 的秒杀只需预热时补一次 |
| 池空时串行补充，其他请求等补充完成后继续 | 账本行锁 + 进程内补充合并（single-flight）+ 补充后立即重试 | BATCHED 模拟中 42 个补充事务服务了 1,321 次合并等待；单 SKU 压测 4,000 次预留只触发 4 次补充 | ✅ 成立，且等待期间不占连接 |
| 复合主键（文章：一个单位从两把锁降到一把） | `PK(shop, item, location, unit_id)` | L1：领取 3 个单位 = 3 个记录锁（PRIMARY）；L5：自增主键 + 二级索引 = 6 个（k_dim + PRIMARY） | ✅ 复现文章结论 |
| READ COMMITTED（文章：RR 在空表上的间隙锁阻塞补充） | 所有写事务显式 RC | L6：RR 下空池锁定读持有 X,GAP 锁，补充 INSERT 锁等待超时；RC 下没有间隙锁，INSERT 立即成功 | ✅ 复现文章结论；秒杀开售前后的空池是高发场景，RC 必须强制 |
| 统一锁顺序（文章：reserve 先 DELETE 单位再 INSERT 预留，消除与 claim 的死锁） | 全局顺序：头 -> 买家额度 -> 账本 -> 分录 -> 单位；reserve 先 SKIP LOCKED 领单位，再插入头 | v1.1 的“先插头”顺序实测出现死锁（见 4.5）；改为与文章一致的“先领单位”后，完整一轮测试 InnoDB 死锁计数器没有增加 | ✅ 成立（v1.2 修订后） |
| UNION ALL 一次往返领取多行 | 第二阶段开关 | L7：每个分支各自 SKIP LOCKED，返回行不与他人锁定行重叠，锁数正确 | ✅ 语法与锁行为成立；秒杀多为单 SKU，收益有限，保持默认关闭 |
| claim 在同一库内同步扣减账本，获得 ACID | SYNC 模式保留；新增 BATCHED | SYNC 单 SKU claim 约 238 次/秒；BATCHED 约 1,210 次/秒 | ⚠️ 秒杀下需改用 BATCHED（仍是同一事务、仍为 ACID，只是账本合并延后，见 7.12） |
| 瓶颈在连接而不是 SQL；SQL 业务标签 + 代理层归因 | 三个连接池舱壁、准入控制、按标签统计连接持有时间 | 设计层面；模拟中 claim 与 reserve 使用独立连接池 | ✅ 采纳；生产若使用 ProxySQL，可直接复用标签 |
| 尝试把多个结账合并进一个 SKIP LOCKED 查询（文章：有帮助但增加复杂度） | 不采用 | 售罄缓存 + 热点许可已把数据库请求量降到成功量级 | ✅ 不需要 |
| 调高 innodb_thread_concurrency | 对照实验（计划） | 未在本地验证 | 上线前在生产规格上验证 |
| 影子双写、按 pod 逐步切换 | 不在本服务范围 | — | 若从现有秒杀系统迁移，建议照文章做影子对比 |

## 4. 实测验证

### 4.1 环境

- Intel i5-12400（12 逻辑核）、32GB 内存、Windows 11、本地 NVMe；
- MySQL 8.4.9 免安装包，`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`、binlog 开启、buffer pool 512MB、`innodb_lock_wait_timeout=1`；
- 参考实现：Node.js + mysql2，事务协议与设计文档一致；应用与数据库在同一台机器上。

**这些数字只用来比较方案之间的相对差异，不是生产容量。** 生产服务器的刷盘延迟、网络往返和 CPU 都不同，上线前必须在生产规格环境重新测量（第 6 节）。

### 4.2 锁行为与约束（locks.js，20/20 通过）

| 编号 | 内容 | 结果 |
| --- | --- | --- |
| L1 | 复合主键下领取 3 个单位的锁数 | 3 个 PRIMARY 记录锁（X,REC_NOT_GAP） |
| L2 | SKIP LOCKED 跳过他人锁定行 | 拿到其余 7 行，不等待 |
| L3 | RC 普通 COUNT 是否能看到未提交删除 | 能看到：未提交删除时 COUNT=10，提交后 7。补充只会少补，不会让池超容量 |
| L4 | RC 下补充 INSERT 是否被在途预留阻塞 | 不阻塞（0ms） |
| L5 | 自增主键 + 二级索引的锁数 | 6 个（每单位 2 个），复现文章 |
| L6 | 空池时 RR 与 RC 的对比 | RR：X,GAP 锁，INSERT 超时；RC：无锁，INSERT 成功 |
| L7 | UNION ALL 多分支 SKIP LOCKED | 返回 2+3 行，不与他人锁定行重叠 |
| C1~C11 | CHECK 约束正反例 | 全部符合预期（修复后，见 4.5） |
| Q1 | 同一买家并发首次下单 | 在额度行上串行化，结果正确 |

### 4.3 秒杀全流程模拟（flashsale.js）

场景：库存 3,000，池容量 1,000（需要多次补充），约 31,500 次请求（含 5% 同幂等键重放），1.2 万买家、限购 2 件，下单数量 1/2/3 件（3 件必然超限），64 个并发；成功后 60% 确认（其中 5% 重复确认）、15% 取消、10% 超时后迟到确认、其余放弃等过期；TTL 5 秒，宽限 1 秒；后台同时运行过期扫描、热点补充、结算。

| 不超卖（已确认 / 库存 3,000） | ✅ 2,460 | ✅ 1,502 | ✅ 2,161 | ✅ 2,475 |
| 限购：任何买家 ≤ 2 件 | ✅ | ✅ | ✅ | ✅ |

| 成功预留 | 3,087 | 2,676 | 2,708 | 3,073 |
| claim 因超过截止时间失败 | **0** | **549** | 0 | 0 |

整轮（锁测试 + 4 个模拟 + 压测）前后，InnoDB 全局计数器 `information_schema.INNODB_METRICS.lock_deadlocks` 保持不变。

SYNC 的已确认量明显偏少，原因是大量确认因排队错过了截止时间（其中一部分随后经 lateClaim 补回）。两种模式最后都剩有余量，是因为模拟中的请求在约 4 秒内结束，而被放弃的预留要在 TTL（5 秒）之后才释放。这符合预期：真实秒杀中这部分“回流库存”会被持续重试的用户买走，售罄缓存最多让回流晚 300ms 可售。

### 4.4 单热点 SKU 压测（bench.js）

| 场景 | SYNC | BATCHED |
| --- | --- | --- |
| reserve，32 并发，4,000 次 | 1,819/s，p50 16ms，p99 38ms | 1,858/s，p50 16ms，p99 45ms |
| claim，16 并发，4,000 次 | **238/s**，p50 66ms，p99 92ms | **1,212/s**，p50 13ms，p99 26ms |
| 取消（释放），16 并发，4,000 次 | **241/s**，p99 80ms | **1,240/s**，p99 30ms |
| 结算 4,000 条分录 | — | 一个事务，54ms |
| 售罄后 5,000 次请求，无缓存 | 5,896 次/秒，每次都访问数据库（158 个补充事务） | 同左 |
| 售罄后 5,000 次请求，缓存 300ms | 90,909 次/秒，只有 32 次访问数据库 | 同左 |

（修复 reserve 加锁顺序之前，“无缓存”一行为 3,674 次/秒：空池时每次都要插入一个预留头再回滚。）

解读：

- reserve 吞吐与结算模式无关，因为 reserve 本来就不碰账本，这正是文章的设计目标。
- SYNC 的 claim / 释放被单个账本行串行化，每次都要持锁到提交刷盘完成，所以吞吐上限约等于 1 ÷ 提交延迟。BATCHED 把这部分负载分散到各自独立的分录行上。
- 每次压测结束后都执行了审计，结果全部有效。

### 4.5 测试发现的缺陷

- **reserve 先插头导致的死锁**：首轮模拟在 SYNC 与“活动中切换”变体中各出现 1~2 次死锁（被有界重试吸收，没有影响正确性）。InnoDB 死锁日志显示：两个事务分别插入相邻的幂等键（k29627、k29628），都在 `uq_reservation_idempotency` 的同一间隙上持有 `S locks gap before rec`，又都在等待 `X insert intention`。原因是 v1.1 的 reserve 先插入预留头，池不足时回滚，留下唯一索引的删除标记记录；重试时用同一个键插入，唯一性检查即使在 RC 下也会加 S 间隙锁。修复：reserve 先用 SKIP LOCKED 领齐单位，确认足量后才写入任何行（7.2），这也是文章自己修复死锁后采用的顺序。修复后完整一轮测试没有新增死锁，空池时的数据库开销也降低了。启示：**任何会在失败时回滚、并以同一唯一键重试的事务，都应该把唯一键插入放在可能失败的检查之后。**
- **CHECK 约束三值逻辑漏洞**：`claim_mode IN ('RESERVED','LATE')` 遇到 NULL 得到 UNKNOWN，MySQL 把 UNKNOWN 当作通过，于是 CLAIMED + claim_mode=NULL 被接受。已改为显式 `IS NOT NULL`，并用 COALESCE 修正 `ck_reservation_expired` 中的同类写法；修复后 C5 通过。今后可空列上的约束一律按这个写法。
- **TTL 下限**：测试误用 3 秒 TTL，被 `ck_reservation_ttl` 正确拒绝，说明约束有效。秒杀 TTL 最短 5 秒；若业务需要更短，必须同时修改契约与约束。

## 5. 方案修订摘要（v1.2）

- 7.12 BATCHED 结算：新表 `ledger_pending_entries`；结算任务；refill / lateClaim / adjust 内联结算；两种模式可随时切换；审计包含分录。
- 7.13 限购：新表 `item_purchase_limits`、`buyer_quotas`；reserve 增加 buyerId；新错误码 BUYER_LIMIT_EXCEEDED。
- 15.2 售罄快速拒绝、可用量查询缓存；7.11 开售预热并把活动 SKU 钉入热点集。
- 7.1 全局锁顺序扩展为：头 -> 买家额度 -> 账本 -> 分录 -> 单位；7.2 reserve 改为先 SKIP LOCKED 领齐单位、再插入头（修复实测死锁）。
- DDL 修复 CHECK 三值逻辑漏洞；DDL 已在 MySQL 8.4.9 上完整执行。

## 6. 上线条件（Go / No-Go 清单）

以下任意一项不满足，都不应把本方案用于生产秒杀：

1. **用正式实现重跑验证**：Java 实现必须通过与 `verification/` 等价的测试（锁行为、全流程模拟、审计），而不仅仅是单元测试。
2. **在生产规格上测容量**：在与生产同规格的 MySQL（相同的刷盘设置、复制方式、网络）上运行单 SKU 压测，得到 reserve 与 claim 的实际上限。要求：活动的峰值成功预留速率 ≤ 实测 reserve 上限的 50%；峰值 claim + 释放速率 ≤ BATCHED 实测上限的 50%。估算方法见第 7 节。
3. **秒杀 SKU 使用 BATCHED 结算、开启售罄缓存、开售前预热**。
4. **上游削峰**：秒杀网关 / 活动服务负责令牌、排队或限流，只放行与库存同一数量级的请求（例如库存的 2~5 倍）进入库存服务；人机校验、防刷、一人多号识别在上游完成。库存服务的准入限流只是兜底。
5. **数据库配置**：`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`（放宽会在崩溃时丢失已提交的 claim，导致超卖）；半同步复制或 MGR（避免切换时丢事务）；业务事务显式 RC；`innodb_lock_wait_timeout` 1~2 秒；连接预算在 `max_connections` 之内。
6. **共享数据库的“好邻居”约束**（文章的最终结论）：如果库存库与订单 / 支付共用主库，必须先用连接标签确认其他调用方没有长时间占用连接，并在压测中同时施加这些调用方的负载。
7. **监控与告警到位**：不变量违例、冻结、待结算分录积压、过期积压、LATE_CLAIM_INSUFFICIENT_STOCK、各连接池的 pending（见 [极端场景与降级预案](极端场景与降级预案.md)）。
8. **演练**：开售洪峰、数据库主从切换、过期任务停摆、结算任务停摆，各演练至少一次，并在演练后审计通过。

## 7. 容量估算方法

```text
需要的峰值成功预留速率 ≈ 活动库存 ÷ 期望售罄时长 × (1 + 回流比例)
需要的峰值 claim + 释放速率 ≈ 峰值成功预留速率（每个预留最终恰好一次确认或释放）
进入库存服务的请求 ≈ 上游放行量；售罄后几乎全部由售罄缓存在应用层拒绝
单 SKU 数据库并发 ≈ 实例数 × 热点维度许可（默认 8）
```

示例：库存 1 万件、期望 10 秒售罄、回流 30%，需要约 1,300 次/秒的成功预留和约 1,300 次/秒的确认 / 释放。在本地环境：reserve（约 1,800/s）满足；SYNC claim（约 240/s）**不满足**；BATCHED claim（约 1,200/s）接近上限，需要在生产规格上确认，或把售罄时长目标放宽到 15 秒。

## 8. 尚未验证的部分

- 多实例（多个应用进程）同时运行。参考实现在单进程内同时运行了预留 facade 和后台补充 / 结算 / 过期任务，跨实例的补充互斥依赖账本行锁，已由并发补充覆盖；多进程部署仍需在正式实现中测试。
- Java 实现、HikariCP 舱壁、熔断与降级等级的实际行为。
- 网络故障注入（Toxiproxy）、主从切换。
- 生产规格硬件上的绝对容量；`innodb_thread_concurrency` 对照。
- 持续数小时的长稳运行（purge 滞后、历史明细增长）。
