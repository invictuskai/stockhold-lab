# 库存预留系统：详细技术方案

状态：设计稿 v1.3。DDL 与核心事务协议已在本地 MySQL 8.4.9 上用参考实现完成实测（见 [秒杀场景评审与验证报告](秒杀场景评审与验证报告.md)）；正式 Java 实现与生产规格压测尚未进行。

v1.3 变更（逻辑库存分区，均有实测依据）：库存维度第三列由“地点”改为“逻辑库存分区”（4.1），营销活动、渠道等上游概念映射为分区而不进入库存服务；新增分区的开启 / 关闭、分区间划拨与关闭后退回（7.14）；限购改为“分区+SKU / 分区合计 / SKU 跨分区”三种范围的规则，并记录每个预留的额度占用（7.13）。

v1.2 变更（秒杀适配，均有实测依据）：账本 BATCHED 结算模式（7.12）、每买家限购（7.13）、售罄快速拒绝与活动预热（15.2、7.11）、可用量查询缓存；修正 CHECK 约束在可空列上的三值逻辑漏洞。

v1.1 变更：对照原文补齐池空时的等待语义（补充成功后立即重试、进程内补充合并）、热点主动补充、claim 宽限与迟到确认、库存维度冻结、负向调整回收池单位、连接池舱壁与分级降级。完整极端场景矩阵见 [极端场景与降级预案](极端场景与降级预案.md)。

## 1. 目标与范围

构建一个可在本地运行的 Java 后端，验证 Shopify 文章的三个主要结论：

1. 热点商品的预留可以从“争抢单个数量行”改为“领取不同库存单位行”。
2. 预留记录与库存账本在同一个 MySQL 中，可以获得本地事务原子性。
3. 查询延迟、事务时长、连接占用、数据库排队必须联合观察。

### 1.1 第一版包含

- 多商家、多 SKU、多逻辑库存分区。`shop_id` 即商家 ID（字段名沿用文章），用于隔离不同商家的库存、预留与幂等键；本方案不引入独立的“租户”概念。
- 逻辑库存分区的开启 / 关闭、分区间划拨、关闭后退回余量；多范围的每买家限购。
- 一个请求包含多个SKU / 分区，整单预留全成功或全失败。
- 每个SKU / 分区可配置的有界池，默认上限 1,000。
- 预留、确认扣减、取消、超时释放、幂等重试。
- 后台补充、热点主动补充和池不足时的同步补充。
- 明确的锁顺序、READ COMMITTED 和短事务。
- 支付成功后的 claim 宽限与迟到确认，冻结异常库存维度。
- 连接池舱壁、准入控制、热点限流与分级降级。
- MySQL 集成测试、多实例并发测试、故障注入、压测与指标。

### 1.2 第一版不包含

- 真正接入支付渠道；支付成功由调用方请求 claim 模拟。
- 跨 MySQL 分片、跨数据中心的原子事务。
- 分区之间自动借用库存；每个预留行必须明确指定分区（默认分区 0），用哪个分区由上游决定。
- 营销概念：活动时间窗口、价格、参与资格都由上游负责；库存服务只认分区与限购规则（4.1）。
- 物理仓储与履约：货从哪个仓库发出由下游履约系统决定，与逻辑库存分区无关。
- 部分确认 / 部分取消；第一版只支持整单状态转换。
- Redis 生产迁移、生产级支付补偿、Kafka / Outbox。
- 无上限的单行购买量；明确限制见第 9 节。

所有参与同一订单预留的库存维度必须在同一个数据库。后续分片按 shop 路由，不能在应用层假装跨分片事务仍然原子。

## 4. 领域模型与不变量

### 4.1 库存维度

`InventoryKey = (shop_id, inventory_item_id, stock_partition_id)`，即（商家, SKU, 逻辑库存分区）。

- **SKU**（`inventory_item_id`）：商家内一个可售库存单元。
- **逻辑库存分区**（`stock_partition_id`）：可售额度的逻辑划分。分区 0 是默认可售分区；其他分区由上游按需创建，例如一场营销活动、一个销售渠道各对应一个分区。它和货物实际放在哪个物理仓库无关，也不叫“仓库区”，以免和仓储系统的物理库区混淆。
- 文章主键的第三列 `inventory_group_id`（库存分组）本来就是这个含义；v1 曾把它解释为“地点”，v1.3 改回分组语义。

**边界：营销概念不进入库存服务。** 以“同一双鞋参加两场活动”为例：

| 上游（营销服务）看到的 | 库存服务看到的 |
| --- | --- |
| 活动 A：¥199，100 双，每人限 1 双 | 分区 7：鞋 H=100；限购规则“分区 7 的鞋，每人 1” |
| 活动 B：¥399，200 双，每人限 2 双 | 分区 8：鞋 H=200；限购规则“分区 8 的鞋，每人 2” |
| 日常销售：¥599 | 分区 0：鞋的剩余库存 |
| 活动开始前备货 / 结束后退回 | 分区间划拨 / 关闭分区并退回余量 |
| 这单按活动 A 的价格成交 | 预留请求的行上带 `stockPartitionId = 7` |
| 活动 A 售罄后是否允许按原价购买 | 库存服务从不跨分区借用；是否改用分区 0 由营销服务决定 |

库存服务不保存价格、时间窗口和参与资格。`stock_partitions.external_ref` 只记录上游引用，用于对账和排查，库存逻辑不读取它。

**每个分区是一个完整独立的库存维度**：账本、单位池、补充、SKIP LOCKED 领取、BATCHED 结算、不变量审计全部按维度独立运行，第 7 节的协议对分区无需任何改动。只有划拨、关闭、退回这三个分区级操作需要同时触及两个维度（7.14）。

### 4.2 关键数量

每个库存维度定义：

| 符号 | 字段 / 计算方法 | 含义 |
| --- | --- | --- |
| H | ledger.on_hand_quantity | 尚未正式售出的账面库存，包含被预留的部分 |
| A | ledger.allocated_quantity | 已发放到“可用池 + ACTIVE 预留”的库存额度 |
| P | reservation_units 行数 | 可用池中的库存单位数量 |
| R | ACTIVE 预留明细 quantity 合计 | 尚未确认或释放的预留总量 |
| F | H - A | 尚未发放为单位行的库存额度 |
| C | ledger.pool_capacity | 可用池上限，默认 1,000 |

在任意已提交的一致性快照中，必须成立：

```text
H >= A >= 0
A = P + R
0 <= P <= C
可再次预留的总量 = H - R = F + P
```

注意：

- `A` 不是预留数量，不能把它直接展示为“已预留”。
- `H` 不是可售数量，因为它包含 ACTIVE 预留。
- ACTIVE 但已经到期、尚未被清理的预留仍计入 R；直到释放事务提交，额度才真正回收。
- BATCHED 结算模式（7.12）下，记未结算分录的增量合计为 dH、dA（均 <= 0），上述不变量对 `H+dH`、`A+dA` 成立；SYNC 模式下 dH = dA = 0。
- 这里的一致性快照不能由多个 RC 普通 SELECT 随意拼接；查询接口和校验器使用单条一致性查询。

### 4.3 为什么引入 allocated_quantity

补充库存池时，如果只看账面库存，可能把已经预留的库存再次展开为单位行。

`allocated_quantity` 为发放额度建立明确边界：

```text
补充 n 个单位：A += n，P += n
预留 n 个单位：P -= n，R += n，A 不变
确认 n 个单位：H -= n，A -= n，R -= n
释放 n 个单位：A -= n，R -= n，H 不变
```

关键收益：**正常预留路径不更新 ledger 的热点计数行**；只有补充、确认、释放、库存调整需要锁账本。

代价：确认与释放仍有单维度账本行竞争。因此本项目不宣称消除了所有热点，只把高频预留的互斥粒度拆散，并通过批量补充摊薄账本锁成本。完整生命周期吞吐必须独立压测。

### 4.4 实例

```text
初始账本：H=100000, A=0, P=0, R=0
补充1000：H=100000, A=1000, P=1000, R=0
预留800： H=100000, A=1000, P=200, R=800
补充800： H=100000, A=1800, P=1000, R=800
确认800： H=99200,  A=1000, P=1000, R=0
```

可用池始终不超过 1,000，但同时预留的总量可以远大于 1,000。

### 5.1 单位行与预留明细

`reservation_units` 一件库存一行；`reserved_quantities` 不需要一件一行，而是按预留维度记录数量。

领取 3 个单位：删除池中选定的 3 行，插入 quantity=3 的预留明细，同一事务提交。单位 ID 是可替代额度的标识，不代表有独立序列号的实物。

### 5.2 主键与外键

- 单位表使用完整维度作为复合聚簇主键，不使用单列自增 ID 再通过二级索引寻找商品。
- UUID 存为 BINARY(16)，Java 生成；HTTP 输出标准 UUID 字符串。
- 第一版使用标准随机 UUID，批量插入前按完整主键排序；不依赖多节点自增协调。随机 ID 碰撞导致重复键时整个补充事务回滚并以新 ID 重试一次，不忽略错误。
- 核心实验表不加外键：避免隐式外键检查锁干扰核心锁协议。应用必须在同一事务中写头与明细，且提供孤儿记录检查。无外键不是通用数据库建模建议。
- 不使用 `INSERT IGNORE` 吞掉库存单位插入错误，插入数量必须准确。

## 6. 状态机及幂等

```text
                 claim（now < claim_deadline_at）
       ACTIVE ----------------------------------> CLAIMED(claim_mode=RESERVED)
         |  \
         |   \ claim + lateClaim（now >= claim_deadline_at，额度仍被持有）
         |    +---------------------------------> CLAIMED(claim_mode=LATE)
         |
         +--- cancel ---------------------------> CANCELLED
         |
         +--- expiry（now >= claim_deadline_at）-> EXPIRED
                                                    |
                  claim + lateClaim（重新取得额度） |
       CLAIMED(claim_mode=LATE) <-------------------+
```

两个时间点：

- `expires_at`：对调用方承诺的保留截止时间，创建时 = 数据库时间 + ttlSeconds。
- `claim_deadline_at`：= expires_at + claim_grace_seconds（默认 30 秒，可配 0..120），**创建时计算并持久化**。普通 claim 与 expiry 都以它为唯一判定线，避免滚动发布期间不同实例配置不一致导致二者判定不同。

宽限期用于吸收支付回调延迟、网络重试和 claim 自身的锁等待；代价是被放弃的预留最多多占用额度 grace 秒。

规则：

- CLAIMED、CANCELLED 是绝对终态。EXPIRED 只允许经显式 lateClaim 转为 CLAIMED，且必须**重新取得额度**（7.6.2），绝不复用已释放的旧额度。
- 普通 claim 要求 ACTIVE 且持头锁后采样的 `now < claim_deadline_at`。
- ACTIVE 但已过 claim_deadline_at（过期任务落后）时，普通 claim 返回 409 RESERVATION_EXPIRED 并提示可 lateClaim；带 lateClaim 时额度仍在 R 中，直接按普通扣减路径完成，claim_mode=LATE。
- expiry 只处理 ACTIVE 且 `now >= claim_deadline_at` 的记录。
- claim 与 expiry 竞争同一预留头行锁，以获得行锁后采样的数据库时间作判定；不是比较 HTTP 请求抵达时间。
- 已经 CLAIMED 的重复 claim 先走幂等返回，不因后来经过截止时间而失效。
- CANCELLED 不支持 lateClaim：取消代表调用方明确放弃；若之后支付仍成功，调用方应新建预留后 claim，或退款。
- TTL 用数据库时间计算，事务内读取 UTC 微秒时间并明确存入变量；不使用应用实例时钟判断到期。
- claim / expiry 必须在 `SELECT ... FOR UPDATE` 返回、确实获得头锁之后，另发一条 `SELECT UTC_TIMESTAMP(6)` 采样。不要在可能等待很久的锁定 SELECT 中顺便取 NOW：MySQL 的该时间值对应语句开始时间，可能早于获得锁。

### 6.1 reserve 幂等

唯一键 `(shop_id, idempotency_key)`；存储规范化请求的 SHA-256。

规范化包含：shop、合并并排序后的 item/partition/quantity、buyerId、显式默认化的 ttlSeconds。不得直接 hash 原始 JSON。

- 相同 key、相同请求：返回同一 reservation，包括其当前终态，不再次扣池。
- 相同 key、不同请求：409 IDEMPOTENCY_CONFLICT。
- 并发首建由数据库唯一约束仲裁；发生重复键后回滚当前事务，再开启新事务查询已有记录。
- 第一版只持久化成功创建的预留；失败 / 回滚请求不占用幂等键。
- 客户端断连、提交结果不明：用相同 key 重试或按 key 查询，不能换 key 再创建。
- 重复 reserve 请求返回的预留若已是 EXPIRED / CANCELLED，调用方应视为本次结账尝试结束，新尝试使用新 key；服务端不会“刷新”旧预留。
- 调用方换 key 重试会产生重复占用，服务端无法区分；由 TTL 回收，并以“同一 shop 短时间内相同请求 hash 的 ACTIVE 预留数”指标暴露异常客户端。

### 6.2 claim 幂等

- claim 携带 paymentReference。
- 已 CLAIMED 且 reference 相同：200，返回原结果。
- 已 CLAIMED 但 reference 不同：409。
- 同一 shop 的 paymentReference 唯一，防止一次支付关联两个预留；数据库唯一约束做最终防线。
- lateClaim 的重放同样按 paymentReference 幂等：已 CLAIMED（无论 RESERVED / LATE）且 reference 相同直接返回。
- 这只是 API 幂等，不提供外部支付与 MySQL 的分布式原子性。lateClaim 失败（LATE_CLAIM_INSUFFICIENT_STOCK）是本系统明确暴露给调用方的补偿点：支付已成功但库存无法兑现，调用方必须退款或人工处理。

### 6.3 cancel / expiry 幂等

- CANCELLED 的重复取消返回 200。
- CLAIMED 不能取消；EXPIRED 返回明确终态冲突。
- 到期任务只处理仍 ACTIVE 且已过 claim_deadline_at 的记录。
- 已过 expires_at 的 ACTIVE 记录可以由 cancel 转为 CANCELLED；二者都完整释放额度，不影响库存正确性。

## 7. 事务与锁协议

### 7.1 统一原则

全部库存写事务显式使用 READ COMMITTED；禁止远程 RPC、睡眠和跨事务循环等待时持有数据库连接。

约定资源顺序：

1. 当前业务操作头：一个 reservation 或 inventory_operation；一个事务不处理多个预留头。
2. 如需账本锁，按 InventoryKey 升序取得全部 ledger 行锁。
3. 按 InventoryKey、unit_id 顺序访问 / 修改单位行。
4. 写入预留明细，再完成头记录状态变更。

全局顺序：**头 -> 买家额度 -> ledger -> 待结算分录 -> units**。reserve 是唯一的例外，它先领单位，理由见表后。

| 事务 | 加锁路径 |
| --- | --- |
| reserve | units（SKIP LOCKED，先领齐）-> 新头 -> 买家额度（仅限购商品）-> 删除 units -> details；不取 ledger |
| refill | ledger -> 分录（内联结算）-> units（仅 INSERT） |
| claim / cancel / expiry / lateClaim(ACTIVE)，SYNC | 已有头 -> 买家额度 -> ledger；不操作 units |
| claim / cancel / expiry，BATCHED | 已有头 -> 买家额度 -> 插入分录；不取 ledger |
| 结算 | ledger -> 分录（只删除已提交分录） |
| lateClaim(EXPIRED) | 已有头 -> 买家额度 -> 全部 ledger（升序）-> 分录 -> units（SKIP LOCKED，仅在 F 不足时） |
| adjust(reclaimPool) | 操作头 -> ledger -> 分录 -> units（SKIP LOCKED） |
| 分区间划拨 | 操作行 -> 两个 ledger（按分区升序）-> 分录 -> 源分区 units（SKIP LOCKED） |
| 关闭后退回 | 两个 ledger（按分区升序）-> 分录 -> 源分区 units（SKIP LOCKED）-> 操作行（新行，不会被等待） |
| freeze / unfreeze、关闭分区 | ledger / stock_partitions 单行 |

除 reserve 外，所有路径都是全局顺序的子序列。

**为什么 reserve 先领单位（v1.2 修订，有实测依据）**：v1.1 的 reserve 先插入预留头，池不足时整体回滚，在唯一索引 `uq_reservation_idempotency` 上留下一条删除标记记录（purge 之前一直存在）。重试时用同一个幂等键再次插入，InnoDB 的唯一性检查即使在 RC 下也会对这条记录加 S 间隙锁；相邻幂等键的两个重试请求各自持有同一间隙的 S 锁、又都等待插入意向锁，形成死锁。实测秒杀模拟中出现了 1~2 次（InnoDB 死锁日志确认就是这个模式）。改成先用 SKIP LOCKED 领齐单位、再写入任何行之后：池不足时事务里什么都没写，回滚不会留下唯一索引的残留；修复后完整测试一轮，InnoDB 全局死锁计数器 `lock_deadlocks` 没有增加。这个顺序也和文章修复死锁后的写法一致（“reserve 先 DELETE 单位，再 INSERT 预留”）。

reserve 先持有单位锁、后插入头或更新买家额度，不会成环：其他事务对单位的访问只有 SKIP LOCKED（不等待）和 INSERT（RC 下单位上只有记录锁、没有间隙锁，插入意向不冲突，见验证 L1、L4），所以没有任何事务会等待 reserve 持有的单位锁。reserve 自身可能阻塞的点有两处：同一幂等键并发首建时的唯一键检查，以及同一买家的额度行；持有这些锁的一方都不会反过来等待单位。未提交的分录行对结算的普通读不可见，不会被任何人等待。

**禁止**：reserve 在已经锁住部分单位行后，直接调用补充并锁 ledger。否则会形成 units -> ledger 与补充 ledger -> units 的反向路径。新增任何事务路径都必须先证明是上表顺序的子序列。

排序不能保证所有死锁消失；唯一键检查、索引锁等仍可能造成死锁，必须提供有界全事务重试。

### 7.2 正常预留事务

事务外：校验数量、合并重复维度、排序、计算请求 hash。池容量第一版创建后固定；校验读取可在事务前完成。

事务内：

```text
BEGIN (READ COMMITTED)
  对排序后的每个 InventoryKey：                      -- 第一步：只加锁，不写任何行
    SELECT unit_id FROM reservation_units
      WHERE shop_id=? AND inventory_item_id=? AND stock_partition_id=?
      ORDER BY unit_id LIMIT ?
      FOR UPDATE SKIP LOCKED
    保存选中的 ID；任一维度不足则抛出 PoolNotReady，整体回滚（此时尚未写入，回滚没有残留）

  所有维度都足量后：
  INSERT reservations(status=ACTIVE, idempotency_key, request_hash, buyer_id,
                      expires_at = UTC_TIMESTAMP(6) + ttl,
                      claim_deadline_at = UTC_TIMESTAMP(6) + ttl + claim_grace ...)
    -- 同一条语句里的 UTC_TIMESTAMP(6) 是同一个值

  若带 buyerId，对每个限购商品（按 item 升序）：
    INSERT INTO buyer_quotas ... ON DUPLICATE KEY UPDATE active_quantity = active_quantity + n
    持行锁读取 active + claimed，超过限购 -> 抛出 BuyerLimitExceeded，整体回滚

    DELETE reservation_units WHERE 完整维度 AND unit_id IN (...选中的ID...)
    校验每个维度的实际删除数 = 请求数量

  INSERT reserved_quantities（每个维度一条）
COMMIT
```

必须删除刚才锁定的精确 ID，不能再执行一个独立的 `DELETE ... LIMIT n`。

在全部单位足量前，不写明细；事务失败时头、单位删除、明细全部回滚，因此整单原子。

reserve 不读取 ledger，因此不在事务内检查冻结状态；冻结由准入层缓存与补充事务拦截（7.10）。

**扫描起点（可选开关）**：所有请求都 `ORDER BY unit_id` 从最小 ID 开始，高并发时每条查询要跳过其他事务已锁的前缀行，成本随并发增长。开关 `reserve.random-start` 开启后先查 `unit_id >= 随机起点`，不足再从头补查一次（同一事务、同样 SKIP LOCKED）。默认关闭，压测证明收益后再启用；两种模式必须通过同一套正确性测试。

### 7.3 池不足时的外层编排

文章的语义是“一个事务补充，其余请求等它完成后直接用满池继续”。本项目在不违反锁顺序的前提下这样实现：

```text
reserve(request):
  准入：降级等级 / 全局并发许可 / 热点维度许可 / 冻结缓存（第 15 节）
  deadline = now + 2s；attempts <= 5；immediateRetries <= 2
  loop:
    r = reserveTx.tryReserve()            -- reserve 舱壁，一次短事务
    成功                          -> 201
    DuplicateIdempotencyKey       -> 新事务按 key 读取 -> 200 重放 / 409 冲突
    PoolNotReady(shortKeys)       -> 事务已完全结束、连接已归还
        对 shortKeys 按 InventoryKey 升序：
            outcome = refillSingleFlight(key, need)
            INSUFFICIENT -> 409 INSUFFICIENT_STOCK（整单，不再重试）
            FROZEN       -> 409 INVENTORY_FROZEN
        全部为 REFILLED / ALREADY_REFILLED 且 immediateRetries 未用完
                                  -> 立即重试，不睡眠
        否则（CONTENDED：池看起来足量但被在途事务锁住）
                                  -> 事务外抖动 20~80ms 后重试
    死锁 1213 / 锁等待超时 1205    -> 已整体回滚，抖动后重试
    连接获取超时 / 数据库不可用     -> 立即 503，不重试，计入熔断
  超过时间 / 次数预算 -> 503 INVENTORY_BUSY
```

**进程内补充合并（single-flight）**：同一实例内，同一 InventoryKey 同时只有一个补充事务；其他需要补充的请求在内存 Future 上等待（上限 500ms），**等待期间不持有数据库连接**。这避免了 N 个请求各自拿一条连接排队等 ledger 行锁——那正是文章所说的连接耗尽。跨实例的补充仍由 ledger 行锁串行化，后来者持锁后重新 COUNT，不会重复补充。Future 超时按 CONTENDED 处理。

合并结果包含 `potentialAvailable`；等待者用自己的需求量重新判断是否 INSUFFICIENT，而不是照搬发起者的结论。

补充成功后立即重试，是为了贴近文章“等待者随后用满池继续”的延迟特征；抖动只用于真正的锁竞争。连续立即重试上限防止在极端争抢下形成无休止的忙循环。

不要在一个还没结束的 reserve 事务中用 REQUIRES_NEW 做补充：外层可能占着锁和连接等待内层，且浪费连接池。

实现为非事务 facade + 多次 TransactionTemplate.execute，回调完全退出之后才启动下一事务。同步补充使用 reserve 舱壁的连接（它是预留流程的一部分），single-flight 保证每实例每维度至多占一条。

**多维度购物车的饥饿**：SKIP LOCKED 不保证公平，大购物车可能在热点竞争中反复缺某一维度。v1 接受该风险并以指标观测（按维度数统计 BUSY 比例）；不引入排队或优先级，避免持锁等待。

### 7.4 补充协议（正确性的核心）

每个补充事务只处理一个 InventoryKey：

```text
BEGIN (READ COMMITTED)
  SELECT on_hand_quantity, allocated_quantity, pool_capacity, status
    FROM inventory_ledger WHERE 完整维度 FOR UPDATE
  不存在 -> INVENTORY_NOT_FOUND；status=FROZEN -> 结果 FROZEN，不补充

  SELECT COUNT(*) FROM reservation_units WHERE 完整维度
    -- 普通一致性读，不加 FOR UPDATE

  free = H - A
  refill = min(C - observedPoolCount, free)

  IF refill > 0:
    UPDATE inventory_ledger SET allocated_quantity = A + refill
    批量 INSERT refill 个 reservation_units
COMMIT
```

补充结果（供 7.3 编排），**按下表自上而下的顺序判定，命中即止**：

| 顺序 | 结果 | 条件 |
| --- | --- | --- |
| 1 | FROZEN | 账本冻结（不补充） |
| 2 | INSUFFICIENT | potentialAvailable = F + observedPoolCount < need（即使本次补充了部分单位也照常提交，结论仍为不足） |
| 3 | REFILLED | refill > 0 |
| 4 | ALREADY_REFILLED | refill = 0，且本进程内该维度最近一次成功补充的完成时间晚于本请求遇到 PoolNotReady 的时间（别人刚补过） |
| 5 | CONTENDED | 其余情况：refill = 0 且 potentialAvailable >= need，池内行可能被在途事务锁住 |

ALREADY_REFILLED 与 CONTENDED 在 SQL 层面无法精确区分（普通 COUNT 看不到锁），因此第 4 条使用进程内时间戳作启发式判断；误判只影响“立即重试还是抖动重试”，不影响正确性。

补充事务的 ledger 锁等待使用会话级 `innodb_lock_wait_timeout = 1`；超时视为 CONTENDED。

为什么 COUNT 不需要锁全部单位？

- 持有 ledger 锁后，其他补充、确认、释放和库存调整被串行化。
- 正常 reserve 可以继续，但它只会让已提交的池行数减少，不会增加池行数。
- 未提交删除在普通一致性读中仍可见，因此统计可能偏高，但不会因其他 reserve 而低估已提交池数量。
- 所以最多少补一些，不会让池超过 C。
- `refill <= H-A` 且更新 A 与插入单位原子提交，保证不重复发放库存。

补充批量插入以固定小批次执行，但全部处于同一个事务；例如每批 100 行，最多 1,000 行。随机 ID 碰撞按事务失败处理，不忽略错误，以新 ID 整体重试一次。

**池看起来满但全被锁住**：若在途 reserve 已锁住池中大部分行但尚未提交，COUNT 仍把它们算入，refill 可能为 0。这只让请求多走一次 CONTENDED 重试；在途事务提交删除后下一次补充即可生效。只有当“单维度在途锁定单位数”接近 C 时才会持续出现，此时应观察 CONTENDED 比例并评估 C 与事务时长，而不是放开容量上限。

**补充事务中途失败**（批次插入失败、连接断开、进程崩溃）：A 的更新与已插入批次一起回滚，账本不变；下一次补充重新计算。

### 7.5 如何区分库存不足与锁竞争

`SKIP LOCKED` 返回的行数不足，不能直接判定售罄。

在补充事务持有 ledger 锁的情况下，使用上述普通 COUNT 得到 P，计算：

```text
potentialAvailable = (H - A) + observedPoolCount
```

- 小于该请求在此维度的需求量：可以判定当前真实可预留量不足。
- 大于等于需求量，但锁定读拿不到：可能有未提交竞争，重试，不能报售罄。

此判断期间 reserve 只能消耗池；账本相关操作被该锁排除，因此 P 的陈旧方向只能让可用量偏高，不会因正在持锁的 reserve 而误报库存不足。

库存判断只是该时刻的结论，不承诺未来取消、补货后仍不足。反过来“足量”也不是承诺，之后仍可能被别人抢走。

**过期任务积压时的少卖**：已过 claim_deadline_at 但尚未释放的 ACTIVE 预留仍计入 R，可能导致 INSUFFICIENT。这是有意的安全方向（少卖不超卖）。v1 不在 reserve 路径内联过期释放——按维度定位过期预留需要扫描该维度全部历史明细，代价不可控——而是通过过期任务扩容与积压告警处理（7.8）。INSUFFICIENT 响应的 details 带 `expiryBacklogSeconds`，供调用方判断是否稍后重试。

### 7.6 claim 确认扣减

#### 7.6.1 普通 claim（及 ACTIVE 上的 lateClaim）

```text
BEGIN (READ COMMITTED)
  SELECT reservations ... FOR UPDATE
  若已 CLAIMED：校验 paymentReference 并幂等返回
  校验 ACTIVE；另发 SELECT UTC_TIMESTAMP(6) 取得 now
  now >= claim_deadline_at 且未带 lateClaim -> 409 RESERVATION_EXPIRED（details.lateClaimAllowed=true）
  claim_mode = (now < claim_deadline_at) ? RESERVED : LATE
  SELECT reserved_quantities（头锁保护，明细不可变）
  按 InventoryKey 排序锁住所有 ledger 行
  对每个维度：
    UPDATE inventory_ledger
      SET on_hand_quantity = on_hand_quantity - n,
          allocated_quantity = allocated_quantity - n
      WHERE 完整维度 AND on_hand_quantity >= n AND allocated_quantity >= n
    校验影响1行，否则是内部不变量损坏，整体回滚报警
  UPDATE reservations SET status='CLAIMED', claim_mode=?, payment_reference=?, claimed_at=now
COMMIT
```

预留明细保留用于审计；ACTIVE 状态才参与 R 的计算。claim 不再删除单位行，因为它们在 reserve 时已经离开可用池。

上面是 SYNC 结算模式。带 buyerId 的预留在锁 ledger 前先更新买家额度（active -= n，claimed += n）。BATCHED 模式下不锁 ledger，改为对每个维度插入一条 CLAIM 分录（dH = dA = −n），条件检查推迟到结算时执行（7.12）。

ACTIVE 上的 lateClaim 与普通 claim 走同一路径：额度一直在 R 中，从未被他人使用，扣减是安全的，仅把 claim_mode 记为 LATE 以便审计“超时后才确认”的比例。

正常情况下 claim 不应因“被其他请求抢光库存”失败：预留已经持有额度。过期、状态冲突、数据库故障、数据损坏是不同错误。

**条件更新影响 0 行**：说明 H 或 A 已小于预留持有量，属于不变量损坏。整个 claim 回滚，返回 500 INVENTORY_INVARIANT_VIOLATION，并在**独立事务**中冻结该维度（7.10）、发出告警。不得为了让 claim 成功而跳过条件或钳制为 0。

**claim 的重试预算大于 reserve**：支付已经成功，claim 失败的代价远高于 reserve。死锁 / 锁等待超时在 5 秒、最多 10 次内整体重试；连接使用 critical 舱壁，不与 reserve 争抢。预算耗尽返回 503，调用方用同一 paymentReference 继续重试；宽限期与 lateClaim 保证“重试期间跨过截止时间”仍有确定的处理路径。

#### 7.6.2 EXPIRED 上的 lateClaim：重新取得额度

旧额度已在 expiry 时归还给 F，可能已被别人预留。lateClaim 必须像新预留一样重新取得额度，但在同一事务内直接完成扣减：

```text
BEGIN (READ COMMITTED)
  SELECT reservations ... FOR UPDATE；状态必须为 EXPIRED（CLAIMED 走幂等，其余 409）
  SELECT reserved_quantities
  按 InventoryKey 升序锁住所有 ledger 行；任一 FROZEN -> 409 INVENTORY_FROZEN
  对每个维度（需求 n）：
    fromFree = min(n, H - A)
    fromPool = n - fromFree
    IF fromPool > 0:
      SELECT unit_id FROM reservation_units WHERE 完整维度
        ORDER BY unit_id LIMIT fromPool FOR UPDATE SKIP LOCKED
      不足：若 (H - A) + 普通 COUNT < n -> LATE_CLAIM_INSUFFICIENT_STOCK
            否则 -> CONTENDED（整体回滚，抖动重试）
      DELETE 这些精确 unit_id；A -= fromPool
    H -= n
  全部维度成功后：
  UPDATE reservations SET status='CLAIMED', claim_mode='LATE', payment_reference=?, claimed_at=now
    -- expired_at 保留，用于审计
COMMIT
```

不变量验证：从 F 取的部分 H 减少、A 不变，要求 fromFree <= H-A，故 H>=A 保持；从池取的部分 P 与 A 同减 fromPool，A=P+R 保持；R 不变（该预留从 EXPIRED 转 CLAIMED，不经过 ACTIVE）。审计式“初始 + 调整 − CLAIMED 明细 = H”仍成立。

锁顺序为 头 -> ledger -> units，与 refill（ledger -> units）一致；reserve 从不取 ledger，因此不会与之成环。

失败时整单回滚，不做部分 lateClaim。LATE_CLAIM_INSUFFICIENT_STOCK 返回后，调用方需要退款或人工处理；该事件单独计数并告警，它是“支付与库存不在同一事务”的残余风险的可观测出口。

### 7.7 cancel / expiry 释放

锁头、验证状态、读取明细、排序锁全部 ledger，与 claim 使用相同顺序。

每个维度执行 `allocated_quantity = allocated_quantity - n WHERE ... AND allocated_quantity >= n`，不修改 H；然后将头置为 CANCELLED 或 EXPIRED，同一事务提交。影响 0 行的处理与 claim 相同：回滚、独立事务冻结维度、告警。

BATCHED 模式下释放不锁 ledger，改为插入 RELEASE 分录（dH = 0，dA = −n）；带 buyerId 时同时 active -= n。

冻结的维度仍允许 claim / cancel / expiry：它们只会减少风险敞口（释放或兑现已有占用），阻止它们反而会让 ACTIVE 预留卡死。cancel 使用 critical 舱壁，expiry 使用 background 舱壁。

第一版不把释放单位直接插回池：

- 避免 release 与 refill 都增加单位行导致容量协调复杂化。
- 回收的额度进入 F，由后台或下一次同步补充转换为单位。
- 避免 release 增加 units -> reservations 的另一条锁路径。

若释放后立即有新请求，最多额外触发一次补充，不丢失库存。

### 7.8 过期扫描

- 非锁定分页扫描 `(status, claim_deadline_at, shop_id, reservation_id)` 索引，只取 `claim_deadline_at <= now` 的候选 ID。
- 每个 ID 使用独立短事务锁头并重新检查；不要一个大事务持有上百个预留头。
- 多实例可以扫描到相同 ID，头锁和状态复查确保只释放一次。
- 扫描器候选分页使用 keyset，不用不断增加 OFFSET。
- 后续若采用 SKIP LOCKED 抢任务，必须重新评估批量持头锁的顺序，不能直接改变协议。

健壮性措施：

- **自适应批量**：基线每秒最多 200 个候选、2 个 worker；积压（最老逾期超过 30 秒）时提升到每秒 1,000 个、4 个 worker，仍是每条独立事务，受 background 舱壁连接数约束，不会挤占 reserve / claim。
- **毒丸记录**：某条预留连续释放失败 3 次（例如账本缺失、不变量违例），记入内存隔离表，指数退避后再试，并冻结相关维度、告警；keyset 游标越过它继续扫描，不让一条坏记录阻塞整个队列。
- **任务停摆**：不会超卖，只会少卖（额度一直被 ACTIVE 占用）。以“最老逾期未释放时长”和“逾期未释放数量”为主告警指标，而不是“任务是否报错”。
- **补救手段**：管理接口可手动触发单次扫描；扫描本身幂等，可随时重复执行。

### 7.9 库存初始化与调整

初始化创建 H=初始数量、A=0 的账本，容量 1..1000；预填充是单独事务，不把初始化成功与池已满混为一谈。

调整使用 operationId 幂等，先插入操作头，再锁 ledger。正向补货执行 H+=delta；负向调整只允许新 H>=A，否则返回 409 STOCK_ALLOCATED。

真实业务中盘亏、损坏必须能减库存，而部分额度可能只是躺在池里。因此负向调整支持 `reclaimPool=true`：

```text
BEGIN (READ COMMITTED)
  INSERT inventory_operations（占位快照）
  SELECT ledger ... FOR UPDATE
  newH = H + delta；newH < 0 或 Long 溢出 -> 400 INVALID_ARGUMENT
  IF newH < A:
    IF NOT reclaimPool -> 409 STOCK_ALLOCATED
    need = A - newH                      -- 必须从池中收回的单位数
    SELECT unit_id FROM reservation_units WHERE 完整维度
      ORDER BY unit_id LIMIT need FOR UPDATE SKIP LOCKED
    不足：若普通 COUNT < need -> 409 STOCK_ALLOCATED（缺口已被 ACTIVE 预留占用，不能强收）
          否则 -> 503 INVENTORY_BUSY（单位被在途 reserve 锁住，稍后用同一 operationId 重试）
    DELETE 这些精确 unit_id；A -= need
  UPDATE ledger SET on_hand_quantity = newH, allocated_quantity = A
  UPDATE inventory_operations 写入最终快照（含 pool_reclaimed_quantity）
COMMIT
```

回收只删除池中未被领取的单位，**永远不会让 ACTIVE 预留失效**；已被预留占用的部分只能等其终态后再调整。容量创建后不可在线修改。

### 7.10 冻结库存维度

冻结是“发现数据可能损坏时停止扩大影响”的安全闸，而不是日常运营开关。

- 触发：claim / release 条件更新影响 0 行、审计 valid=false、毒丸记录、人工操作。
- 效果：refill 与 lateClaim(EXPIRED) 拒绝该维度；准入层缓存（每秒刷新，允许最多约 1 秒陈旧）使新 reserve 直接返回 409 INVENTORY_FROZEN；缓存陈旧期间放行的 reserve 只能消耗池内已发放的额度，池耗尽后因补充被拒而失败，不会超发。
- 不阻止：claim、cancel、expiry、查询与审计。
- 解冻：只能由管理接口在审计通过后执行；解冻不自动修复数据。修复通过带 operationId 的调整完成，保留审计轨迹。
- 冻结写入在独立短事务中进行（ledger 单行更新），不与引发冻结的失败事务合并。

### 7.11 后台与热点主动补充

后台补充保证常规维度的池水位，热点补充让热点维度尽量不走同步补充路径。二者都只是优化，正确性不依赖它们及时执行。

- **PoolRefillJob**：每秒 keyset 扫描一批维度，普通 COUNT 低于容量 25% 且 F>0 时补满；最多 2 个 worker，使用 background 舱壁。
- **HotKeyRefiller**：某维度 10 秒内触发同步补充 >= 3 次即进入热点集（每实例最多 200 个，60 秒无触发自动移出）。每 100ms 对热点做一次普通 COUNT，低于 50% 且 F>0 时执行补充事务。
- 多实例重复探测无害：补充由 ledger 行锁串行化，持锁后重新 COUNT。
- 维度数量巨大时，全量每秒扫描不可扩展；届时改为“最近被预留过的维度”候选队列。v1 只在实验规模运行。
- **活动预热（秒杀）**：开售前通过管理接口对活动 SKU 执行补充，把池填满，并把这些维度钉入热点集（不因 60 秒无触发而移出），避免开售第一波请求全部走同步补充。

### 7.12 账本结算模式：SYNC 与 BATCHED

**问题**：文章消除的是 reserve 对单一数量行的争抢，但 claim 仍同步扣减账本。秒杀时同一 SKU 的确认与超时释放集中爆发，每次都要锁同一账本行，行锁持有到提交（含 redo / binlog 刷盘），这一行重新成为热点。实测（本地 MySQL，双 1 刷盘）单 SKU 的 SYNC claim 约 238 次/秒、p99 约 90ms；秒杀模拟中有 549~626 次 claim（多轮结果）因排队超过确认截止时间而失败。

**BATCHED 模式**：

- claim / cancel / expiry 在持预留头锁的同一事务内，对每个维度插入一条 `ledger_pending_entries` 分录（CLAIM：dH = dA = −n；RELEASE：dH = 0，dA = −n），**不锁 ledger**。分录主键含 reservation_id，各请求写不同的行，没有共享热点。
- 结算：锁 ledger -> 普通读取该维度已提交的分录（每批最多 500 条）-> 一次 `UPDATE ledger SET H = H + ΣdH, A = A + ΣdA`（带非负条件）-> 按精确主键删除这些分录，并校验删除行数。由结算任务（有分录的维度每 100~200ms 一次）以及 refill、lateClaim(EXPIRED)、adjust（持 ledger 锁时先内联结算）执行。内联结算每次最多处理 2,000 条，控制 ledger 锁的持有时间。
- 实测：同一 SKU 的 BATCHED claim 约 1,210 次/秒、p99 26~29ms（约为 SYNC 的 5 倍），释放同样约 5 倍；结算 4,000 条分录耗时 54~65ms；所有 BATCHED 秒杀模拟（包括活动中切换模式、停掉结算任务）均 0 次 claim 超时。

**正确性**：

- 不变量写作 `H+dH >= A+dA >= 0`、`A+dA = P+R`。CLAIM 分录在结算前仍计入 H 与 A，不影响 F = H − A；RELEASE 分录在结算前仍计入 A，因此这部分额度暂时不可再售——只会少卖，不会超卖；下一次补充会先内联结算，立即回收这部分额度。
- 结算更新的条件失败或删除行数不符，视为不变量违例：回滚、冻结维度、告警。
- SYNC 与 BATCHED 两条路径在任意时刻都维持同一组不变量，因此 `settlement_mode` 可以随时切换，无需停写；claim 用普通读取模式值，读到旧值也正确。
- 审计与快照把分录合计纳入计算（11 节）。

**监控**：待结算分录数、最老分录的存在时长（超过 5 秒告警）、单次结算批量与耗时。

**选择**：秒杀 / 爆款 SKU 使用 BATCHED；普通商品可以保持 SYNC（更简单，与文章一致）。判断标准：当单 SKU 的预期峰值 claim + 释放速率超过该环境实测 SYNC 单行吞吐的 50% 时，切换为 BATCHED。

### 7.13 每买家限购

限购是营销规则，但**必须在库存服务里执行**：它要和“占库存”在同一事务里生效，否则会出现“额度扣了但没抢到”或“抢到了但额度没记上”。库存服务把它抽象成通用规则——“买家在某范围内最多持有 N 件（ACTIVE + 已确认）”，范围只用库存服务自己的概念描述，不知道规则来自哪场活动。

**规则范围**（`purchase_limit_rules`，可同时命中多条，全部满足才通过）：

| scope_type | 范围 | 对应的营销表述（举例） |
| --- | --- | --- |
| PARTITION_ITEM | 某分区的某 SKU | 活动 A 的这双鞋每人 1 双 |
| PARTITION_TOTAL | 某分区的全部 SKU 合计 | 活动 B 每人共限 2 件，不限款式 |
| ITEM_ALL_PARTITIONS | 某 SKU 跨全部分区（含默认分区） | 这双鞋全渠道每人最多 3 双 |

用 0 / −1 作“不适用”的哨兵而不是 NULL：唯一键里 NULL 互不相等，无法阻止重复规则。

**协议**：

- reserve（领齐单位、插入头之后，删除单位之前）：查出所有命中的 ACTIVE 规则，按 rule_id 升序逐条执行 `INSERT INTO buyer_quotas ... ON DUPLICATE KEY UPDATE active_quantity = active_quantity + q`，持行锁复查 `active + claimed <= limit`，超限即整单回滚（409 BUYER_LIMIT_EXCEEDED，不消耗库存）；同时把 (预留, 规则, q) 写入 `reservation_quota_usages`。命中规则但没有 buyerId 时返回 400 BUYER_ID_REQUIRED。
- claim：按占用明细逐条 active −= q、claimed += q；cancel / expiry：active −= q。
- lateClaim(EXPIRED)：按占用明细 claimed += q，只对仍为 ACTIVE 的规则复查限购，超限返回 409 BUYER_LIMIT_EXCEEDED（支付已成功，调用方需要退款）。
- buyerId 参与请求 hash；同一幂等键的重放不会再次占用额度。

**为什么要记录占用明细**：确认和释放必须按“创建时实际占用了哪些额度行”原路退回，不能按当时的规则重新计算。规则可能在活动中途被改值、停用或新增；如果重新计算，就会去扣一个从没加过的额度行，计数立刻错乱（若有 CHECK 兜底则表现为事务失败）。

**规则变更语义**：

- 改限购值：直接更新规则行，只影响之后的校验。
- 停用：置 DISABLED，不再参与校验；已有占用照常原路退回。
- 删除后重建：得到新 rule_id，计数从零开始——这是有意的语义，需要“清零”时才这样做。
- 新增规则：只约束之后的预留，之前的预留没有占用记录，退回时不会误扣。

**并发**：每个“买家 × 规则”一行，不同买家互不竞争；同一买家的并发请求在这一行上串行化，这正是限购需要的语义。多条规则按 rule_id 升序加锁，顺序固定。

**实测**：两个分区、两个 SKU、四条规则（覆盖三种范围）的并发场景下，没有任何买家突破任何一条规则；额度表与占用明细逐条一致。边界测试覆盖了缺少 buyerId、超限、中途改值 / 停用 / 新增规则后的原路退回。

限购只能防止同一 buyerId 多买，无法识别同一个人使用多个账号；防刷、人机校验属于上游职责。

### 7.14 逻辑库存分区：划拨、关闭与退回

分区内的预留、确认、释放、补充、结算全部沿用前面各节的协议。本节只描述涉及两个维度或分区状态的操作。

**分区状态**（`stock_partitions`）：OPEN 可预留；CLOSED 后不再接受新预留、不再补充、不接受划入，已有预留照常确认 / 取消 / 过期。分区 0 不可关闭（CHECK 约束保证）。

- reserve 在事务开头普通读取分区状态（不加锁），CLOSED 返回 409 STOCK_PARTITION_CLOSED；refill 持账本锁后检查，CLOSED 时不补充。
- 和关闭并发、读到旧状态的 reserve 仍是合法预留：它只能消费池里已有的单位，退回流程会等它终结（见下）。所以关闭是业务闸门，不是正确性依赖。

**划拨**（从分区 S 到分区 D 划 n 件同一 SKU，一个本地事务）：

```text
BEGIN (READ COMMITTED)
  D 必须为 OPEN，否则 409 STOCK_PARTITION_CLOSED
  INSERT inventory_operations 两行（同一 operation_id）：line 1 TRANSFER_OUT（S，−n），line 2 TRANSFER_IN（D，+n）
    -- 先写操作行：同一 operation_id 的并发重放由主键冲突仲裁
  按分区升序锁两个账本（D 不存在则 INSERT ... ON DUPLICATE KEY UPDATE 创建，按同样顺序取得锁）
  两个维度各自内联结算未结算分录
  若 S 的 H < n -> 409 INSUFFICIENT_STOCK
  newH = H_S − n
  IF newH < A_S：                          -- 部分额度躺在池里
    need = A_S − newH
    SKIP LOCKED 锁定 S 池中 need 个单位；不足时：普通 COUNT < need -> 409 STOCK_ALLOCATED（缺口被 ACTIVE 占用）
                                                否则 -> 503 INVENTORY_BUSY（被在途预留锁住，稍后重试）
    删除这些单位，A_S −= need
  H_S = newH，H_D += n
  回写两行操作记录的结果快照
COMMIT
```

划拨永远不会让 ACTIVE 预留失效：被 ACTIVE 占用的额度不能划走，只能等它们终结。

**关闭后退回**（把已关闭分区 P 的余量退回分区 D，通常是 0）：

1. 关闭分区 P。
2. 等 P 的 ACTIVE 预留全部终结（确认、取消或过期）。退回事务里如果发现仍有 ACTIVE，返回 409 ACTIVE_RESERVATIONS_REMAIN，由退回任务稍后重试。
3. 退回事务：按分区升序锁 P 和 D 的账本，内联结算后，把 P 的全部 H 划回 D；P 池里剩余的单位全部回收（被在途预留锁住时返回 503 BUSY，稍后重试）；退回数量只有在锁定账本后才知道，所以操作行在账本锁之后写入。
4. 竞态兜底：如果某个与关闭并发的预留在 ACTIVE 计数之后才提交，“退回全部 H”需要回收的单位数会超过池里的单位数，事务以 STOCK_ALLOCATED 失败，不会把被占用的额度划走。

退回之后，P 上的 EXPIRED 预留若再迟到确认，会因为 P 已没有库存而返回 LATE_CLAIM_INSUFFICIENT_STOCK；是否允许改从分区 0 兑现属于营销决策，库存服务不自动跨分区借用。退回之前（已关闭但仍有余量）迟到确认可以照常从 P 重新取得额度。

**锁顺序**：操作行 -> 账本（按分区升序）-> 分录 -> 单位，是全局顺序的子序列。同一 SKU 的两个分区账本在主键上相邻，按分区升序加锁即可避免两个反向划拨互相等待。

**审计**：

- 每个维度：本维度操作记录 delta 之和 − 本维度 CLAIMED 明细 = H + dH（划出为负、划入为正）。
- 每个 SKU 跨全部分区：Σ(H + dH) = 初始 + 调整 − 已确认，所有划拨行之和必须为 0。

**实测**：同一双鞋同时在默认分区和两个分区销售，抢购进行中完成一次追加划拨，关闭分区 A 后有约 7 千次预留被拒绝，退回任务等待 ACTIVE 清零后退回约 450 件（其中约 380 件从池中回收）；每个维度和 SKU 合计的审计全部成立，无死锁。边界测试覆盖了需要回收池单位的划拨、被 ACTIVE 挡住的划拨、幂等重放、关闭后拒绝预留 / 补充 / 划入、单位被锁时退回返回 BUSY、仍有 ACTIVE 时拒绝退回、退回后迟到确认。

**上游如何使用**（以营销活动为例，库存服务只看到右侧的调用）：

| 上游动作 | 库存服务调用 |
| --- | --- |
| 创建活动并备货 100 件 | 创建分区 7（external_ref=活动 ID）；从分区 0 划拨 100 件到分区 7；配置分区 7 的限购规则 |
| 开售前 | 把分区 7 的结算模式设为 BATCHED，预热补充 |
| 活动中追加库存 | 再从分区 0 划拨到分区 7 |
| 活动结束 | 关闭分区 7；退回任务把余量退回分区 0 |

## 8. RC、索引与 SQL 批处理

### 8.1 隔离级别

所有写事务显式设置 RC。RC 不是“没有任何间隙锁”：外键、重复键检查等仍有特定锁行为。

使用复合主键、锁定精确单位行，是为了减少无关索引访问和锁成本。不能把“一行一个锁”当作所有执行计划的绝对保证；通过 performance_schema.data_locks 和实际执行计划验证。

### 8.2 UNION ALL 分阶段实施

第一版采用“一个事务，多条按维度排序的 SELECT”，优先验证正确性。

第二阶段用功能开关提供候选优化：

```sql
(SELECT inventory_item_id, stock_partition_id, unit_id
 FROM reservation_units
 WHERE shop_id=? AND inventory_item_id=? AND stock_partition_id=?
 ORDER BY unit_id LIMIT ? FOR UPDATE SKIP LOCKED)
UNION ALL
(SELECT inventory_item_id, stock_partition_id, unit_id
 FROM reservation_units
 WHERE shop_id=? AND inventory_item_id=? AND stock_partition_id=?
 ORDER BY unit_id LIMIT ? FOR UPDATE SKIP LOCKED);
```

此 SQL 为待实测方案，不是已运行证据。必须在锁定的 MySQL 版本验证语法、各分支锁行为、缺行分组、执行计划和全事务回滚。外层加 FOR UPDATE 不能替代子查询正确加锁。

不要依赖优化器按文本顺序获得所有锁。reserve 不会等待已锁单位，但删除和唯一约束等仍需死锁重试。优化前后必须运行相同正确性测试。

降级：UNION ALL 路径若出现非预期错误（语法 / 结果分组异常 / 返回行不属于请求维度），当前请求立即回滚并改走逐维度 SELECT 重试，同时本实例自动关闭该开关并告警；只能人工重新开启。结果校验（每行维度必须属于请求、每维度行数 <= LIMIT）在两种模式下都执行。

## 9. 1,000 上限和接口数量边界

- 池上限是每个SKU / 分区的可领取行数，不是该 SKU 在该分区的总库存，也不是同时预留数量。
- 创建库存时 capacity 可设为 1..1000；默认 1000，之后不可修改。
- 单次请求合并后的单维度 quantity 必须 <= 对应 capacity。
- 最多 20 个合并维度；整单最多 1000 个库存单位，限制事务锁数和 DELETE 参数规模。
- 同一维度分成多个输入行不能绕过上限，必须先合并再校验。
- 因此一次购买同一SKU / 分区的 1500 件在 v1 返回 422 QUANTITY_LIMIT_EXCEEDED，不会永久等待补充。

未来若支持大单，需要单独协议，例如分阶段额度分配或专用批量路径。不能一边持有已领取单位锁一边循环补充，也不能多个已提交小预留假装成一个原子大订单。

## 10. 超时、重试与故障处理

### 10.1 超时与预算

初始实验配置（均需压测校准，不是生产推荐值）：

| 项目 | reserve | claim / cancel | background（refill / expiry / 审计） |
| --- | --- | --- | --- |
| 业务重试预算 | 2 秒，最多 5 次 | 5 秒，最多 10 次 | 单次任务内不重试，下个周期再来 |
| 连接获取超时 | 200ms（快速失败） | 1s | 2s |
| 会话 innodb_lock_wait_timeout | 1s | 2s | 1s |
| 单条语句超时（JDBC queryTimeout） | 1s | 2s | 5s（审计查询） |
| 事务总时长上限（应用计时，超出即回滚） | 1s | 3s | 5s |
| 抖动 | 补充成功后立即重试；竞争 20~80ms | 50~150ms | 调度抖动 0~200ms |

- JDBC `socketTimeout` 大于最大语句超时，只作为网络黑洞的最后防线。
- Hikari `maxLifetime` 小于 MySQL `wait_timeout`，并开启 keepalive，避免拿到已被服务端关闭的连接。
- 各预算不是所有阻塞的硬截止线（例如 GC 停顿、内核网络栈），不能宣称绝对上限。

### 10.2 错误分类

| 错误 | 示例 | 事务状态 | 处理 |
| --- | --- | --- | --- |
| 可重试并发冲突 | 死锁 1213 / SQLSTATE 40001、锁等待超时 1205、SKIP LOCKED 不足 | 已整体回滚 | 在预算内抖动重试整个事务 |
| 提交结果不明 | COMMIT 时连接断开、socket 超时 | 未知 | 不盲目重放；reserve 用同一幂等键重试（唯一键仲裁），claim 按头状态 + paymentReference 判定，refill 天然可重入，adjust 用 operationId |
| 数据库不可用 | 连接拒绝、1040 连接过多、1290 / 1836 只读、磁盘满 | 已失败 | 立即 503 DATABASE_UNAVAILABLE，不内部重试，计入熔断 |
| 连接池耗尽 | Hikari 获取超时 | 未开始 | 503 / 429，不映射成库存不足 |
| 业务拒绝 | 数量越界、幂等冲突、状态冲突、真实不足 | 已回滚或未开始 | 不重试，返回确定错误码 |
| 不变量违例 | 条件更新影响 0 行、删除数不符 | 已回滚 | 500，独立事务冻结维度，告警，不重试 |
| 未知异常 | 其他 SQLException / 运行时异常 | 已回滚 | 500 INTERNAL_ERROR；调用方先查询状态再决定是否重试 |

- MySQL 锁等待超时默认只回滚当前语句而非整个事务（innodb_rollback_on_timeout=OFF），Spring 回调必须抛出异常使整个事务回滚，不能捕获后继续提交。
- 所有重试不得扩大为无界线程或无界队列；重试间隔的睡眠发生在事务外、且不持有连接。

### 10.3 进程与数据库故障

- **进程崩溃 / 被杀**：未提交事务由 InnoDB 回滚；已提交的 ACTIVE 预留由过期任务最终释放；single-flight 的等待者随进程一起消失，客户端按幂等重试。
- **优雅停机**：先摘除流量与停止准入 -> 等待在途请求最多 10 秒 -> 停止后台任务 -> 关闭连接池。滚动发布期间多版本共存，因此截止时间等判定参数必须持久化在数据行上（claim_deadline_at），不依赖实例配置。
- **长时间停顿（GC / 宿主机挂起）且持有事务**：ledger 行锁可能被长期持有，其他 claim 锁等待超时。应用侧事务总时长上限只能在恢复后生效；数据库侧用运维巡检发现 `information_schema.innodb_trx` 中超过 5 秒的事务并告警，实验环境可由脚本 KILL。
- **主库故障切换**：在途事务丢失，按“提交结果不明”处理；连接池驱逐旧连接；恢复写入前确认新主 `super_read_only=OFF`。若复制为异步，切换可能**丢失已提交事务**（预留、claim 消失），这超出本服务可保证的范围：生产必须使用半同步复制或 Group Replication，切换后对受影响维度运行审计，发现违例即冻结。本实验只模拟、不宣称解决。
- **purge 滞后**：高频 DELETE / INSERT 会产生大量删除标记记录；若主库存在长事务（例如分析查询或打开很久的 RR 快照），purge 被阻塞，SKIP LOCKED 扫描需要跳过越来越多的删除标记行，reserve 延迟逐步恶化。措施：禁止在主库运行长事务（`max_execution_time`、分析走副本），监控 `trx_rseg_history_len`，超过阈值告警。
- **数据库时间跳变**：所有到期判定使用数据库 UTC 时间；小幅回拨 / 前跳由宽限期吸收，大幅跳变视为基础设施事故，需人工确认后再恢复过期任务。会话统一 `time_zone='+00:00'`。

## 11. 一致性查询与审计

库存查询返回 H、A、P、R、F 和 effectiveAvailable=H-R。使用一条 SQL 对 ledger、单位计数和 ACTIVE 明细计数进行独立聚合再组合，不能直接把两张一对多表 JOIN 后 SUM 导致乘法重复。

单维度库存快照的示意 SQL（参数绑定由 JDBC 完成，待 MySQL 实测）：

```sql
SELECT l.shop_id, l.inventory_item_id, l.stock_partition_id,
       l.on_hand_quantity, l.allocated_quantity, l.pool_capacity,
       (SELECT COUNT(*)
          FROM reservation_units u
         WHERE u.shop_id = l.shop_id
           AND u.inventory_item_id = l.inventory_item_id
           AND u.stock_partition_id = l.stock_partition_id) AS pool_available_quantity,
       (SELECT COALESCE(SUM(q.quantity), 0)
          FROM reserved_quantities q
          JOIN reservations r
            ON r.shop_id = q.shop_id AND r.reservation_id = q.reservation_id
         WHERE q.shop_id = l.shop_id
           AND q.inventory_item_id = l.inventory_item_id
           AND q.stock_partition_id = l.stock_partition_id
           AND r.status = 'ACTIVE') AS active_reserved_quantity
  FROM inventory_ledger l
 WHERE l.shop_id = ? AND l.inventory_item_id = ? AND l.stock_partition_id = ?;
```

其余派生数量在应用中从该行结果计算；这条只读查询不加 FOR UPDATE。库存读取与 claim 等写入必须访问主库，第一版不引入副本延迟语义。

BATCHED 模式下在同一条 SQL 中再汇总 `ledger_pending_entries` 的 ΣdH、ΣdA，用 `H+ΣdH`、`A+ΣdA` 校验不变量（参考实现见 `verification/lib.js` 的 audit）。

校验器针对稳定测试结束点或单条一致性快照验证：

1. H>=A>=0。
2. A=P+R。
3. P<=capacity。
4. 没有孤儿明细、非法终态、重复幂等预留。
5. 初始库存 + 累计调整 - CLAIMED 明细（含 claim_mode=LATE）= H；池回收不改变该等式（回收只减 A）。
6. 预留失败或回滚没有残留 ACTIVE 头 / 明细 / 单位丢失。
7. 没有 ACTIVE 预留的 claim_deadline_at 早于“当前时间 − 允许积压阈值”（否则是过期任务故障，而非数据损坏，单独归类）。

第五条需要保留 inventory_operations 与 CLAIMED 明细。设计阶段不做自动历史清理；压测数据用专门环境重置。

审计与快照查询按维度扫描全部历史明细，成本随历史增长；在 L1 及以上降级等级中关闭（第 15 节），且只允许单维度调用。长期运行需要“审计检查点 + 终态记录归档”，列为 M5。

审计发现违例时只报告并冻结，不自动修复：自动修复可能把一次误判变成真实的数据破坏。

## 12. 可观测性

应用指标：

- reserve / claim / cancel / expiry / refill 的吞吐与 P50/P95/P99。
- reserve 重试次数、SKIP LOCKED 缺行、真实不足和 BUSY 分别统计。
- 每次补充数量、补充耗时、同步补充比例。
- 连接获取等待时间与获取成功后到 close 的持有时间，按固定业务标签归因。
- 事务持续时间与 SQL 执行时间分开测量。
- Hikari active / idle / pending / timeout，按 reserve / critical / background 舱壁分别统计。
- 过期清理落后时间、待清理数量、不变量校验失败。
- 补充结果分布（REFILLED / ALREADY_REFILLED / CONTENDED / INSUFFICIENT / FROZEN）、single-flight 合并等待时长与超时数、热点集大小。
- claim_mode=LATE 比例、LATE_CLAIM_INSUFFICIENT_STOCK 次数（每一次都意味着需要退款）。
- 准入拒绝（429）按原因统计：全局许可、热点维度许可、降级等级；熔断状态变化；当前降级等级。
- 冻结维度数量、毒丸记录数量、UNION ALL 自动关闭事件。
- 数据库侧 `trx_rseg_history_len`、最长运行事务时长。

SQL 固定白名单标签：

```sql
/* conn_tag:reserve */
/* conn_tag:claim */
/* conn_tag:cancel */
/* conn_tag:refill */
/* conn_tag:expiry */
/* conn_tag:admin */
```

告警与处置对照见 [极端场景与降级预案](极端场景与降级预案.md) 第 5 节。

标签禁止包含用户输入、paymentReference、UUID、商品 ID，避免 SQL 注入、敏感数据泄漏及指标高基数。原始业务标识仅按需要写入受控日志。

数据库侧：CPU、Threads_running、连接数、锁等待、死锁、InnoDB 事务时长、data_locks / data_lock_waits；使用独立管理连接观察，避免监控争抢业务连接池。

应用 Hikari 连接持有时间不等同于 ProxySQL 的后端连接占用时间。代理复用和事务固定会影响二者；ProxySQL 是后续独立实验，不把应用指标冒充代理证据。

## 13. 安全与资源边界

- API 中的 shopId 在本地实验显式传入；生产需由鉴权上下文校验，不能仅相信路径参数。
- 库存初始化、调整、手动补充、不变量扫描属于实验管理接口，仅 dev profile 开放并要求独立管理令牌。
- 参数化 SQL，所有查询必须带 shop 维度。
- 限制请求行数、合并后数量、TTL、请求体大小和并发请求数。
- 恶意占库存（大量预留从不支付）：TTL 上限 900 秒是兜底；可选的“每 shop ACTIVE 预留单位数上限”在准入层以近似计数实现（超出返回 429）。买家级限流属于上游结账服务职责。
- 数据库配置使用环境变量，不提交真实凭据；业务账号与迁移账号分离。
- 默认只监听本地；容器数据库端口绑定 127.0.0.1。

## 14. 性能预期与已知取舍

本项目不会预先承诺某个 QPS，也不拿 Shopify 的每分钟销售额当请求吞吐。

需要实测的核心问题：

- 单热点 reserve 是否比单计数器路径有更小的锁等待？
- 池容量从 50 到 1000，补充频率、扫描成本、P99 如何变化？
- 大量 ACTIVE 预留会增长 reserved_quantities；有界池只约束可用单位表，不约束全部历史数据。
- claim / release 对 ledger 的串行化是否成为下一瓶颈？
- 多商品整单预留在高争抢时是否出现饥饿与回滚放大？SKIP LOCKED 不保证公平。
- TTL 太短是否让成功预留因重试和排队而迅速过期？
- 连接池大小、长事务、线程并发配置如何影响吞吐？不得直接调大所有限制。
- 自增主键 vs 复合主键的每次预留锁数量（复现文章“两把锁变一把”）。
- `innodb_thread_concurrency` 调整前后在“CPU 未满但排队”场景下的吞吐变化（复现文章的配置结论）。
- 补充成功后立即重试 vs 固定抖动、single-flight 开关、随机扫描起点开关对热点 P99 的影响。

正确性优先。允许返回可重试的 BUSY，但不允许把锁竞争报成售罄、允许重复发放额度，或仅靠缓存计数掩盖账本不一致。

## 15. 过载保护与降级

文章的核心教训是：瓶颈往往是连接而不是 SQL，而预留必须是共享数据库的“好邻居”。本节的所有措施都遵循以下优先级：

1. **正确性 > 可用性 > 延迟**。任何降级都不能放松不变量。
2. **服务端永远 fail-closed**：未在数据库提交就不返回成功。是否在预留不可用时“无预留放行结账”（fail-open，接受超卖风险）是调用方的业务决策，本服务只提供明确的错误码、`retryable` 与当前降级等级。
3. **少卖优于超卖**：不确定时占着额度，而不是放出额度。
4. **先舍新请求，保在途请求**：优先级 claim > cancel > expiry > reserve > 后台补充 > 审计 / 管理。
5. **一切有界**：并发、队列、重试、等待时长、热点集大小都有上限。

### 15.1 连接池舱壁

三个独立 HikariDataSource，各自的 TransactionTemplate 与连接归因：

| 舱壁 | 用途 | 初始大小（每实例） | 获取超时 |
| --- | --- | --- | --- |
| reserve | reserve、同步补充 | 16 | 200ms |
| critical | claim、cancel、lateClaim、按 ID / 幂等键查询 | 8 | 1s |
| background | refill job、热点补充、expiry、审计、管理接口 | 4 | 2s |

- 目的：reserve 洪峰或后台任务失控不能让 claim 拿不到连接。
- 所有实例的舱壁总和必须小于 MySQL `max_connections` 减去运维 / 监控 / 迁移预留，部署清单中显式计算。
- 大小为实验起点，由压测校准；不得通过无限调大连接池掩盖长事务。

### 15.2 准入控制

在进入 facade 之前、获取连接之前执行，拒绝不消耗数据库资源：

- **全局并发许可**：每实例 reserve 并发上限 = reserve 舱壁大小 × 2；等待许可最多 20ms，超时 429 TOO_MANY_REQUESTS。不设无界排队。
- **热点维度许可**：同一 InventoryKey 每实例最多 8 个并发 reserve；超出 429 INVENTORY_THROTTLED。防止单个爆款的洪峰占满全部连接，其余商品照常可售。多维度购物车按其中最热的维度判定。
- **冻结缓存**：命中冻结维度直接 409 INVENTORY_FROZEN。
- **分区状态与限购规则缓存**：两者都是配置类数据。参考实现在 reserve 事务内普通读取它们（分区状态 1 次、规则匹配 1 次），claim 多读 1 次占用明细；实测单 SKU reserve 吞吐约下降 15%（约 1.8k/s 降到约 1.5k/s）、BATCHED claim 约下降 15%。生产实现可以在准入层缓存分区状态和规则（每秒刷新）以消除这部分开销，代价是：新关闭的分区最多晚约 1 秒拒绝预留（退回流程本身保证不会丢失或误划额度），新增规则最多晚约 1 秒生效。因此限购规则应在开售前配置好，活动中改规则不能指望立即生效。
- **售罄快速拒绝（秒杀）**：一次 refill 判定 INSUFFICIENT 后，本实例缓存该维度的 `potentialAvailable` 300ms（可配置）；有效期内需求量大于缓存值的请求直接返回 409 INSUFFICIENT_STOCK，不访问数据库。缓存期间，其他预留只会让真实可用量变小（缓存偏高，请求照常进入数据库判定）；只有取消 / 释放回流会让真实值超过缓存值，这时请求会被误拒。所以误判仅限于缓存期内的回流库存，最多晚 300ms 才能卖出（少卖，不超卖），并且绝不会因此放行超卖。实测售罄阶段 5,000 次请求只有 32 次访问数据库，处理能力从约 5,900 次/秒（无缓存，每次都访问数据库）提高到约 9 万次/秒。
- **可用量查询（秒杀页轮询）**：`GET .../availability` 返回 `F + P`（含未结算分录修正）的近似值，只读 ledger 一行、计数不超过 1,000 行的池、汇总少量分录，不扫描历史明细；每实例缓存 500ms，数据库负载与轮询量无关。完整快照接口（11 节）不得用于前台展示。
- **熔断**：reserve 路径在 10 秒窗口内数据库类错误（10.2 中“数据库不可用 / 连接池耗尽”）比例超过 50% 且请求数 >= 20 时打开，打开期间直接 503 SERVICE_DEGRADED；5 秒后半开放行少量探测。claim 路径不熔断：支付已成功，只要数据库可用就必须尝试。
- 429 / 503 均带 `Retry-After`，客户端必须抖动退避并沿用原幂等键。

### 15.3 降级等级

运行时开关（Actuator 端点 + 配置，实例级生效，可按 shop 覆盖），自动熔断只会把 reserve 推到 L2，不会自动进入 L3：

| 等级 | 触发 | 行为 |
| --- | --- | --- |
| L0 NORMAL | 默认 | 全部功能 |
| L1 PROTECT | Hikari pending 持续升高、P99 超阈值、history list 过长，人工或自动 | 关闭 UNION ALL 与随机起点等实验开关；reserve 重试预算降为 1 秒 / 2 次；后台补充只保留热点；关闭快照 / 审计接口；过期任务保持基线速率 |
| L2 SHED | 熔断打开或人工 | 新 reserve 直接 503 SERVICE_DEGRADED；claim / cancel / expiry 与幂等查询照常 |
| L3 WRITE_FREEZE | 数据库切换、维护、疑似大面积数据损坏，仅人工 | 所有写接口 503；读接口在数据库可达时照常；过期任务暂停（少卖，不超卖） |

- 降级与恢复都记录事件与原因；从 L2/L3 恢复时先恢复 claim / expiry，再逐步放开 reserve（每实例许可按 25% 阶梯恢复），避免恢复瞬间的惊群。
- 单计数器对照模式与单位池模式**不能**在同一数据上运行时切换：两者的账本语义不同，切换需要停写、迁移并审计。

### 15.4 单点开关汇总

| 开关 | 默认 | 关闭 / 打开后的效果 |
| --- | --- | --- |
| reserve.union-all | 关 | 打开后多维度一次往返；异常自动关闭 |
| reserve.random-start | 关 | 打开后分散扫描起点 |
| reserve.single-flight | 开 | 关闭后退化为各请求独立补充（仍正确，连接占用更高） |
| refill.hot-key | 开 | 关闭后热点只靠同步补充与普通后台任务 |
| refill.background | 开 | 关闭后只靠同步补充；正确性不受影响 |
| expiry.enabled | 开 | 关闭后少卖，必须伴随告警 |
| claim.grace-seconds | 30 | 只影响之后新建的预留（截止时间已持久化） |

## 16. 残余风险与明确边界

以下风险在本设计中被**暴露和观测**，而非被消除：

| 风险 | 为什么无法在本服务内消除 | 本设计的处理 |
| --- | --- | --- |
| 支付成功但库存无法兑现 | 支付渠道与 MySQL 不在同一事务 | 宽限期 + lateClaim 最大化兑现；失败返回 LATE_CLAIM_INSUFFICIENT_STOCK 并告警，由调用方退款 |
| 异步复制切换丢失已提交事务 | 数据库复制层面的持久性问题 | 要求半同步 / MGR；切换后审计与冻结 |
| 调用方换幂等键重复预留 | 服务端无法识别语义重复 | TTL 回收 + 指标暴露 |
| 调用方选择 fail-open | 业务决策 | 返回明确错误码与降级等级，不替调用方决定 |
| 过期任务长时间停摆 | 依赖后台进程 | 少卖而非超卖；积压告警 |
| 热点竞争下的大购物车饥饿 | SKIP LOCKED 不保证公平 | 有界重试 + BUSY + 指标 |
| 历史明细无限增长 | v1 不做归档 | 审计限单维度；归档列入 M5 |
| 一人多号绕过限购、机器人抢购 | 身份与风控不在库存服务内 | 限购按 buyerId 原子执行；防刷由上游负责 |
| 单个 MySQL 主库的单 SKU 成功预留上限 | 单位池仍在一个库、一个维度内 | 秒杀的成功量受库存约束（库存 ÷ 售罄时长）；上线前必须在生产规格上实测，超出时需在上游削峰或拆分活动库存 |
