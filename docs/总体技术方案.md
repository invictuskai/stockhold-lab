# 库存预留系统：详细技术方案

状态：设计稿 v1，未完成实现或数据库执行验证。

## 1. 目标与范围

构建一个可在本地运行的 Java 后端，验证 Shopify 文章的三个主要结论：

1. 热点商品的预留可以从“争抢单个数量行”改为“领取不同库存单位行”。
2. 预留记录与库存账本在同一个 MySQL 中，可以获得本地事务原子性。
3. 查询延迟、事务时长、连接占用、数据库排队必须联合观察。

### 1.1 第一版包含

- 多租户 shop、多商品、多地点库存。
- 一个请求包含多个商品 / 地点，整单预留全成功或全失败。
- 每个商品 / 地点可配置的有界池，默认上限 1,000。
- 预留、确认扣减、取消、超时释放、幂等重试。
- 后台补充和池不足时的同步补充。
- 明确的锁顺序、READ COMMITTED 和短事务。
- MySQL 集成测试、多实例并发测试、压测与指标。

### 1.2 第一版不包含

- 真正接入支付渠道；支付成功由调用方请求 claim 模拟。
- 跨 MySQL 分片、跨数据中心的原子事务。
- 自动选择履约地点、拆单、调拨；调用方必须明确指定地点。
- 部分确认 / 部分取消；第一版只支持整单状态转换。
- Redis 生产迁移、生产级支付补偿、Kafka / Outbox。
- 无上限的单行购买量；明确限制见第 9 节。

所有参与同一订单预留的库存维度必须在同一个数据库。后续分片按 shop 路由，不能在应用层假装跨分片事务仍然原子。

## 4. 领域模型与不变量

### 4.1 库存维度

`InventoryKey = (shop_id, inventory_item_id, location_id)`。

文章中的 `inventory_group_id` 在本项目中不照搬其内部语义，显式使用 `location_id`。

### 4.2 关键数量

每个库存维度定义：

| 符号 | 字段 / 计算方法 | 含义 |
| --- | --- | --- |
| H | ledger.on_hand_quantity | 尚未正式售出的账面库存，包含被预留的部分 |
| A | ledger.allocated_quantity | 已发放到“可用池 + ACTIVE 预留”的库存额度 |
| P | reservation_units 行数 | 可用池中的库存单位数量 |
| R | ACTIVE 预留明细 quantity 合计 | 尚未确认或释放的预留总量 |
| F | H - A | 尚未发放为单位行的库存额度 |
| C | ledger.pool_capacity | 可用池上限，默认 1,000 |

在任意已提交的一致性快照中，必须成立：

```text
H >= A >= 0
A = P + R
0 <= P <= C
可再次预留的总量 = H - R = F + P
```

注意：

- `A` 不是预留数量，不能把它直接展示为“已预留”。
- `H` 不是可售数量，因为它包含 ACTIVE 预留。
- ACTIVE 但已经到期、尚未被清理的预留仍计入 R；直到释放事务提交，额度才真正回收。
- 这里的一致性快照不能由多个 RC 普通 SELECT 随意拼接；查询接口和校验器使用单条一致性查询。

### 4.3 为什么引入 allocated_quantity

补充库存池时，如果只看账面库存，可能把已经预留的库存再次展开为单位行。

`allocated_quantity` 为发放额度建立明确边界：

```text
补充 n 个单位：A += n，P += n
预留 n 个单位：P -= n，R += n，A 不变
确认 n 个单位：H -= n，A -= n，R -= n
释放 n 个单位：A -= n，R -= n，H 不变
```

关键收益：**正常预留路径不更新 ledger 的热点计数行**；只有补充、确认、释放、库存调整需要锁账本。

代价：确认与释放仍有单维度账本行竞争。因此本项目不宣称消除了所有热点，只把高频预留的互斥粒度拆散，并通过批量补充摊薄账本锁成本。完整生命周期吞吐必须独立压测。

### 4.4 实例

```text
初始账本：H=100000, A=0, P=0, R=0
补充1000：H=100000, A=1000, P=1000, R=0
预留800： H=100000, A=1000, P=200, R=800
补充800： H=100000, A=1800, P=1000, R=800
确认800： H=99200,  A=1000, P=1000, R=0
```

可用池始终不超过 1,000，但同时预留的总量可以远大于 1,000。

## 5. 数据表

完整定义见 [数据库表结构.sql](数据库表结构.sql)。

| 表 | 作用 | 主要索引 |
| --- | --- | --- |
| inventory_ledger | 真实库存及已发放额度 | PK(shop, item, location) |
| reservation_units | 可领取单位行，一行一个单位 | PK(shop, item, location, unit_id) |
| reservations | 预留头、状态、幂等、过期时间 | PK(shop, reservation_id)，幂等唯一键，状态过期索引 |
| reserved_quantities | 预留明细，一行一个商品 / 地点的数量 | PK(shop, reservation_id, line_no) |
| inventory_operations | 初始化 / 调整库存的幂等操作记录 | PK(shop, operation_id) |

### 5.1 单位行与预留明细

`reservation_units` 一件库存一行；`reserved_quantities` 不需要一件一行，而是按预留维度记录数量。

领取 3 个单位：删除池中选定的 3 行，插入 quantity=3 的预留明细，同一事务提交。单位 ID 是可替代额度的标识，不代表有独立序列号的实物。

### 5.2 主键与外键

- 单位表使用完整维度作为复合聚簇主键，不使用单列自增 ID 再通过二级索引寻找商品。
- UUID 存为 BINARY(16)，Java 生成；HTTP 输出标准 UUID 字符串。
- 第一版使用标准随机 UUID，批量插入前按完整主键排序；不依赖多节点自增协调。
- 核心实验表不加外键：避免隐式外键检查锁干扰核心锁协议。应用必须在同一事务中写头与明细，且提供孤儿记录检查。无外键不是通用数据库建模建议。
- 不使用 `INSERT IGNORE` 吞掉库存单位插入错误，插入数量必须准确。

## 6. 状态机及幂等

```text
             claim
       ACTIVE -------> CLAIMED
         |
         +--- cancel -> CANCELLED
         |
         +--- expiry -> EXPIRED
```

- 状态只允许上述转换，终态不可复活。
- `expires_at <= 数据库当前时间` 时不允许新 claim。
- claim 与 expiry 竞争同一预留头行锁，以获得行锁后采样的数据库时间作判定；不是比较 HTTP 请求抵达时间。
- 已经 CLAIMED 的重复 claim 先走幂等返回，不因后来经过 expires_at 而失效。
- TTL 用数据库时间计算，事务内读取 UTC 微秒时间并明确存入变量；不使用应用实例时钟判断到期。
- claim / expiry 必须在 `SELECT ... FOR UPDATE` 返回、确实获得头锁之后，另发一条 `SELECT UTC_TIMESTAMP(6)` 采样。不要在可能等待很久的锁定 SELECT 中顺便取 NOW：MySQL 的该时间值对应语句开始时间，可能早于获得锁。

### 6.1 reserve 幂等

唯一键 `(shop_id, idempotency_key)`；存储规范化请求的 SHA-256。

规范化包含：shop、合并并排序后的 item/location/quantity、显式默认化的 ttlSeconds。不得直接 hash 原始 JSON。

- 相同 key、相同请求：返回同一 reservation，包括其当前终态，不再次扣池。
- 相同 key、不同请求：409 IDEMPOTENCY_CONFLICT。
- 并发首建由数据库唯一约束仲裁；发生重复键后回滚当前事务，再开启新事务查询已有记录。
- 第一版只持久化成功创建的预留；失败 / 回滚请求不占用幂等键。
- 客户端断连、提交结果不明：用相同 key 重试或按 key 查询，不能换 key 再创建。

### 6.2 claim 幂等

- claim 携带 paymentReference。
- 已 CLAIMED 且 reference 相同：200，返回原结果。
- 已 CLAIMED 但 reference 不同：409。
- 同一 shop 的 paymentReference 唯一，防止一次支付关联两个预留；数据库唯一约束做最终防线。
- 这只是 API 幂等，不提供外部支付与 MySQL 的分布式原子性。

### 6.3 cancel / expiry 幂等

- CANCELLED 的重复取消返回 200。
- CLAIMED 不能取消；EXPIRED 返回明确终态冲突。
- 到期任务只处理仍 ACTIVE 且已到期的记录。
- 到期的 ACTIVE 记录可以由 cancel 转为 CANCELLED；二者都完整释放额度，不影响库存正确性。

## 7. 事务与锁协议

### 7.1 统一原则

全部库存写事务显式使用 READ COMMITTED；禁止远程 RPC、睡眠和跨事务循环等待时持有数据库连接。

约定资源顺序：

1. 当前业务操作头：一个 reservation 或 inventory_operation；一个事务不处理多个预留头。
2. 如需账本锁，按 InventoryKey 升序取得全部 ledger 行锁。
3. 按 InventoryKey、unit_id 顺序访问 / 修改单位行。
4. 写入预留明细，再完成头记录状态变更。

补充事务只有 ledger -> units；正常 reserve 为新头 -> units -> details，不取 ledger 行锁；claim / cancel / expiry 为已有头 -> ledger，不操作 units。

**禁止**：reserve 在已经锁住部分单位行后，直接调用补充并锁 ledger。否则会形成 units -> ledger 与补充 ledger -> units 的反向路径。

排序不能保证所有死锁消失；唯一键检查、索引锁等仍可能造成死锁，必须提供有界全事务重试。

### 7.2 正常预留事务

事务外：校验数量、合并重复维度、排序、计算请求 hash。池容量第一版创建后固定；校验读取可在事务前完成。

事务内：

```text
BEGIN (READ COMMITTED)
  INSERT reservations(status=ACTIVE, idempotency_key, request_hash, expires_at...)

  对排序后的每个 InventoryKey：
    SELECT unit_id FROM reservation_units
      WHERE shop_id=? AND inventory_item_id=? AND location_id=?
      ORDER BY unit_id LIMIT ?
      FOR UPDATE SKIP LOCKED
    保存选中的 ID；任一维度不足则抛出 PoolNotReady，整体回滚

  所有维度都足量后：
    DELETE reservation_units WHERE 完整维度 AND unit_id IN (...选中的ID...)
    校验每个维度的实际删除数 = 请求数量

  INSERT reserved_quantities（每个维度一条）
COMMIT
```

必须删除刚才锁定的精确 ID，不能再执行一个独立的 `DELETE ... LIMIT n`。

在全部单位足量前，不写明细；事务失败时头、单位删除、明细全部回滚，因此整单原子。

### 7.3 池不足时的外层编排

```text
attemptReserve()
  成功 -> 返回
  PoolNotReady -> 确保事务整体结束，释放连接
    对不足维度逐个执行独立 replenish 事务
    若证明真实不足 -> 409 INSUFFICIENT_STOCK
    否则在事务外带抖动重试整个 reserve
    超过时间 / 次数预算 -> 503 INVENTORY_BUSY
```

不要在一个还没结束的 reserve 事务中用 REQUIRES_NEW 做补充：外层可能占着锁和连接等待内层，且浪费连接池。

建议实现为非事务 facade + 多次 TransactionTemplate.execute，回调完全退出之后才启动下一事务。

多个请求需要补充同一维度时，补充事务竞争同一 ledger 行锁；后来者获得锁后重新检查池，不重复盲目补充。正常已有足量单位的 reserve 仍能并行运行。

### 7.4 补充协议（正确性的核心）

每个补充事务只处理一个 InventoryKey：

```text
BEGIN (READ COMMITTED)
  SELECT on_hand_quantity, allocated_quantity, pool_capacity
    FROM inventory_ledger WHERE 完整维度 FOR UPDATE

  SELECT COUNT(*) FROM reservation_units WHERE 完整维度
    -- 普通一致性读，不加 FOR UPDATE

  free = H - A
  refill = min(C - observedPoolCount, free)

  IF refill > 0:
    UPDATE inventory_ledger SET allocated_quantity = A + refill
    批量 INSERT refill 个 reservation_units
COMMIT
```

为什么 COUNT 不需要锁全部单位？

- 持有 ledger 锁后，其他补充、确认、释放和库存调整被串行化。
- 正常 reserve 可以继续，但它只会让已提交的池行数减少，不会增加池行数。
- 未提交删除在普通一致性读中仍可见，因此统计可能偏高，但不会因其他 reserve 而低估已提交池数量。
- 所以最多少补一些，不会让池超过 C。
- `refill <= H-A` 且更新 A 与插入单位原子提交，保证不重复发放库存。

补充批量插入以固定小批次执行，但全部处于同一个事务；例如每批 100 行，最多 1,000 行。随机 ID 碰撞按事务失败处理，不忽略错误。

### 7.5 如何区分库存不足与锁竞争

`SKIP LOCKED` 返回的行数不足，不能直接判定售罄。

在补充事务持有 ledger 锁的情况下，使用上述普通 COUNT 得到 P，计算：

```text
potentialAvailable = (H - A) + observedPoolCount
```

- 小于该请求在此维度的需求量：可以判定当前真实可预留量不足。
- 大于等于需求量，但锁定读拿不到：可能有未提交竞争，重试，不能报售罄。

此判断期间 reserve 只能消耗池；账本相关操作被该锁排除，因此 P 的陈旧方向只能让可用量偏高，不会因正在持锁的 reserve 而误报库存不足。

库存判断只是该时刻的结论，不承诺未来取消、补货后仍不足。反过来“足量”也不是承诺，之后仍可能被别人抢走。

### 7.6 claim 确认扣减

```text
BEGIN (READ COMMITTED)
  SELECT reservations ... FOR UPDATE
  若已 CLAIMED：校验 paymentReference 并幂等返回
  校验 ACTIVE；获取数据库当前时间，校验未过期
  SELECT reserved_quantities（头锁保护，明细不可变）
  按 InventoryKey 排序锁住所有 ledger 行
  对每个维度：
    UPDATE inventory_ledger
      SET on_hand_quantity = on_hand_quantity - n,
          allocated_quantity = allocated_quantity - n
      WHERE 完整维度 AND on_hand_quantity >= n AND allocated_quantity >= n
    校验影响1行，否则是内部不变量损坏，整体回滚报警
  UPDATE reservations SET status='CLAIMED', payment_reference=?, claimed_at=?
COMMIT
```

预留明细保留用于审计；ACTIVE 状态才参与 R 的计算。claim 不再删除单位行，因为它们在 reserve 时已经离开可用池。

正常情况下 claim 不应因“被其他请求抢光库存”失败：预留已经持有额度。过期、状态冲突、数据库故障、数据损坏是不同错误。

### 7.7 cancel / expiry 释放

锁头、验证状态、读取明细、排序锁全部 ledger，与 claim 使用相同顺序。

每个维度执行 `allocated_quantity -= quantity`，不修改 H；然后将头置为 CANCELLED 或 EXPIRED，同一事务提交。

第一版不把释放单位直接插回池：

- 避免 release 与 refill 都增加单位行导致容量协调复杂化。
- 回收的额度进入 F，由后台或下一次同步补充转换为单位。
- 避免 release 增加 units -> reservations 的另一条锁路径。

若释放后立即有新请求，最多额外触发一次补充，不丢失库存。

### 7.8 过期扫描

- 非锁定分页扫描 `(status, expires_at, shop_id, reservation_id)` 索引，只取候选 ID。
- 每个 ID 使用独立短事务锁头并重新检查；不要一个大事务持有上百个预留头。
- 多实例可以扫描到相同 ID，头锁和状态复查确保只释放一次。
- 扫描器候选分页使用 keyset，不用不断增加 OFFSET。
- 后续若采用 SKIP LOCKED 抢任务，必须重新评估批量持头锁的顺序，不能直接改变协议。

### 7.9 库存初始化与调整

初始化创建 H=初始数量、A=0 的账本，容量 1..1000；预填充是单独事务，不把初始化成功与池已满混为一谈。

调整使用 operationId 幂等，先插入操作头，再锁 ledger。正向补货执行 H+=delta；负向调整只允许新 H>=A，否则返回 409 STOCK_ALLOCATED。

该限制刻意保守：即使一部分额度只是放在池中，也不直接允许减掉它。第一版不实现池回收 / 强制减库存，避免隐藏单位删除和已预留订单失效。容量创建后不可在线修改。

## 8. RC、索引与 SQL 批处理

### 8.1 隔离级别

所有写事务显式设置 RC。RC 不是“没有任何间隙锁”：外键、重复键检查等仍有特定锁行为。

使用复合主键、锁定精确单位行，是为了减少无关索引访问和锁成本。不能把“一行一个锁”当作所有执行计划的绝对保证；通过 performance_schema.data_locks 和实际执行计划验证。

### 8.2 UNION ALL 分阶段实施

第一版采用“一个事务，多条按维度排序的 SELECT”，优先验证正确性。

第二阶段用功能开关提供候选优化：

```sql
(SELECT inventory_item_id, location_id, unit_id
 FROM reservation_units
 WHERE shop_id=? AND inventory_item_id=? AND location_id=?
 ORDER BY unit_id LIMIT ? FOR UPDATE SKIP LOCKED)
UNION ALL
(SELECT inventory_item_id, location_id, unit_id
 FROM reservation_units
 WHERE shop_id=? AND inventory_item_id=? AND location_id=?
 ORDER BY unit_id LIMIT ? FOR UPDATE SKIP LOCKED);
```

此 SQL 为待实测方案，不是已运行证据。必须在锁定的 MySQL 版本验证语法、各分支锁行为、缺行分组、执行计划和全事务回滚。外层加 FOR UPDATE 不能替代子查询正确加锁。

不要依赖优化器按文本顺序获得所有锁。reserve 不会等待已锁单位，但删除和唯一约束等仍需死锁重试。优化前后必须运行相同正确性测试。

## 9. 1,000 上限和接口数量边界

- 池上限是每个商品 / 地点的可领取行数，不是地点总库存，也不是同时预留数量。
- 创建库存时 capacity 可设为 1..1000；默认 1000，之后不可修改。
- 单次请求合并后的单维度 quantity 必须 <= 对应 capacity。
- 最多 20 个合并维度；整单最多 1000 个库存单位，限制事务锁数和 DELETE 参数规模。
- 同一维度分成多个输入行不能绕过上限，必须先合并再校验。
- 因此一次购买同一商品 / 地点的 1500 件在 v1 返回 422 QUANTITY_LIMIT_EXCEEDED，不会永久等待补充。

未来若支持大单，需要单独协议，例如分阶段额度分配或专用批量路径。不能一边持有已领取单位锁一边循环补充，也不能多个已提交小预留假装成一个原子大订单。

## 10. 超时、重试与故障处理

初始实验配置（均需压测校准，不是生产推荐值）：

- reserve 总业务重试预算：2 秒，最多 5 次；50~150ms 事务外抖动。
- 锁等待：独立实验数据库设置 innodb_lock_wait_timeout=1 秒。
- JDBC statement / transaction timeout、连接获取超时另行配置并测量；不能宣称总预算是所有阻塞的硬截止线。
- 死锁 1213 / SQLSTATE 40001、锁等待超时 1205：回滚整个事务后重试。
- MySQL 锁等待超时默认未必回滚整个事务，Spring 回调必须抛出异常明确回滚，不能捕获后继续提交。
- 网络故障 / 提交结果不明：通过幂等键或 reservation 状态重查；未知异常不能盲目重放非幂等逻辑。
- 数据库断开 / 连接池耗尽：503，不映射成库存不足。
- 请求到期、数量非法、幂等冲突：不做内部重试。
- 所有重试不得扩大为无界线程或无界队列；应用层提供有限并发入口。

进程崩溃时，未提交事务由 InnoDB 回滚；已经提交的 ACTIVE 预留由过期任务最终释放。到期任务停机不会超卖，但会暂时减少可售量，必须监控释放延迟。

## 11. 一致性查询与审计

库存查询返回 H、A、P、R、F 和 effectiveAvailable=H-R。使用一条 SQL 对 ledger、单位计数和 ACTIVE 明细计数进行独立聚合再组合，不能直接把两张一对多表 JOIN 后 SUM 导致乘法重复。

单维度库存快照的示意 SQL（参数绑定由 JDBC 完成，待 MySQL 实测）：

```sql
SELECT l.shop_id, l.inventory_item_id, l.location_id,
       l.on_hand_quantity, l.allocated_quantity, l.pool_capacity,
       (SELECT COUNT(*)
          FROM reservation_units u
         WHERE u.shop_id = l.shop_id
           AND u.inventory_item_id = l.inventory_item_id
           AND u.location_id = l.location_id) AS pool_available_quantity,
       (SELECT COALESCE(SUM(q.quantity), 0)
          FROM reserved_quantities q
          JOIN reservations r
            ON r.shop_id = q.shop_id AND r.reservation_id = q.reservation_id
         WHERE q.shop_id = l.shop_id
           AND q.inventory_item_id = l.inventory_item_id
           AND q.location_id = l.location_id
           AND r.status = 'ACTIVE') AS active_reserved_quantity
  FROM inventory_ledger l
 WHERE l.shop_id = ? AND l.inventory_item_id = ? AND l.location_id = ?;
```

其余派生数量在应用中从该行结果计算；这条只读查询不加 FOR UPDATE。库存读取与 claim 等写入必须访问主库，第一版不引入副本延迟语义。

校验器针对稳定测试结束点或单条一致性快照验证：

1. H>=A>=0。
2. A=P+R。
3. P<=capacity。
4. 没有孤儿明细、非法终态、重复幂等预留。
5. 初始库存 + 累计调整 - CLAIMED 明细 = H。
6. 预留失败或回滚没有残留 ACTIVE 头 / 明细 / 单位丢失。

第五条需要保留 inventory_operations 与 CLAIMED 明细。设计阶段不做自动历史清理；压测数据用专门环境重置。

## 12. 可观测性

应用指标：

- reserve / claim / cancel / expiry / refill 的吞吐与 P50/P95/P99。
- reserve 重试次数、SKIP LOCKED 缺行、真实不足和 BUSY 分别统计。
- 每次补充数量、补充耗时、同步补充比例。
- 连接获取等待时间与获取成功后到 close 的持有时间，按固定业务标签归因。
- 事务持续时间与 SQL 执行时间分开测量。
- Hikari active / idle / pending / timeout。
- 过期清理落后时间、待清理数量、不变量校验失败。

SQL 固定白名单标签：

```sql
/* conn_tag:reserve */
/* conn_tag:claim */
/* conn_tag:refill */
/* conn_tag:expiry */
```

标签禁止包含用户输入、paymentReference、UUID、商品 ID，避免 SQL 注入、敏感数据泄漏及指标高基数。原始业务标识仅按需要写入受控日志。

数据库侧：CPU、Threads_running、连接数、锁等待、死锁、InnoDB 事务时长、data_locks / data_lock_waits；使用独立管理连接观察，避免监控争抢业务连接池。

应用 Hikari 连接持有时间不等同于 ProxySQL 的后端连接占用时间。代理复用和事务固定会影响二者；ProxySQL 是后续独立实验，不把应用指标冒充代理证据。

## 13. 安全与资源边界

- API 中的 shopId 在本地实验显式传入；生产需由鉴权上下文校验，不能仅相信路径参数。
- 库存初始化、调整、手动补充、不变量扫描属于实验管理接口，仅 dev profile 开放并要求独立管理令牌。
- 参数化 SQL，所有查询必须带 shop 维度。
- 限制请求行数、合并后数量、TTL、请求体大小和并发请求数。
- 数据库配置使用环境变量，不提交真实凭据；业务账号与迁移账号分离。
- 默认只监听本地；容器数据库端口绑定 127.0.0.1。

## 14. 性能预期与已知取舍

本项目不会预先承诺某个 QPS，也不拿 Shopify 的每分钟销售额当请求吞吐。

需要实测的核心问题：

- 单热点 reserve 是否比单计数器路径有更小的锁等待？
- 池容量从 50 到 1000，补充频率、扫描成本、P99 如何变化？
- 大量 ACTIVE 预留会增长 reserved_quantities；有界池只约束可用单位表，不约束全部历史数据。
- claim / release 对 ledger 的串行化是否成为下一瓶颈？
- 多商品整单预留在高争抢时是否出现饥饿与回滚放大？SKIP LOCKED 不保证公平。
- TTL 太短是否让成功预留因重试和排队而迅速过期？
- 连接池大小、长事务、线程并发配置如何影响吞吐？不得直接调大所有限制。

正确性优先。允许返回可重试的 BUSY，但不允许把锁竞争报成售罄、允许重复发放额度，或仅靠缓存计数掩盖账本不一致。
