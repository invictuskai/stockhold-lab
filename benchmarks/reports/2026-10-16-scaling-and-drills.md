# 2026-10-16 扩展性与故障演练：连接数、多实例、进程崩溃、ProxySQL、Redis 影子迁移

承接 [2026-10-15 单位池 vs 单计数器](2026-10-15-unit-pool-vs-counter.md)，补齐当时列为“未验证”的项目。环境与方法相同（同一台 M1 Max，MySQL 8.4.11 在 colima 虚拟机中，k6 与应用同机），代码为 commit `7275e1b` 起的连接优化版本。仍然是**单机相对比较，不是生产容量结论**。原始数据：[raw/2026-10-16-scaling](raw/2026-10-16-scaling)、[raw/2026-10-16-drills](raw/2026-10-16-drills)。

**无法完成的一项**：独立的数据库服务器需要另一台物理机器。本报告的 MySQL 仍与应用、k6 共享同一台主机的 CPU，这一点对 E7 / E8 的上限有直接影响，见下文。

## 一句话结论

| 实验 | 结论 |
| --- | --- |
| E7 连接数扫描 | 单位池随连接数提升（8 → 64 连接：1,024 → 1,785 次/秒，+74%），证实上一份报告“卡在连接上”的推测；单计数器纹丝不动（577 → 583），多出的连接只在那一把行锁前排队。64 连接时单位池约为单计数器的 3.1 倍 |
| E8 多应用实例 | 1 → 2 个进程单位池 +11%，3 个进程持平；同机的 3 个 JVM + k6 + 虚拟机先把主机用满。单计数器随实例增多反而略降。多实例同时运行补充 / 过期任务、跨实例确认，正确性全部通过 |
| E9 进程崩溃 | 两实例跑完整生命周期时 `kill -9` 其中一个、26 秒后重启：客户端用同一幂等键换实例重试，57,264 个预留**一个不多一个不少**，4 次“已提交但响应丢失”被幂等重放正确恢复，0 次最终失败 |
| E10 ProxySQL 归因 | 用 Connector/J 默认设置连接 ProxySQL 时，每个客户端连接都钉住一个后端连接，代理退化为直通；加一条 `multiplex=2` 查询规则后复用恢复。复用正常时，“拿着连接不执行 SQL”让吞吐降 42%，但**在代理侧完全不可见**——只看代理归因会漏掉元凶 |
| E11 Redis 影子迁移 | 两实例、90 秒完整生命周期中按“Redis 为主 → MySQL 为主 → 回切 → MySQL 为主”切换：58,554 个预留与全部确认 / 取消无一失败，影子比对 0 处不一致，静止后两系统在 73 秒内收敛到完全相同的状态 |

所有记录在案的运行与演练都通过了不变量审计。

## E7：连接数扫描（单热点，只预留，100 并发）

| Hikari 连接数 | 单位池 成功/s | 单位池 P99 | 单计数器 成功/s | 单计数器 P99 |
| --- | --- | --- | --- | --- |
| 8 | 1,024 (982–1,028) | 313 ms | — | — |
| 16 | 1,366 (1,363–1,370) | 241 ms | 577 (573–579) | 248 ms |
| 32 | 1,586 (1,571–1,602) | 291 ms | — | — |
| 64 | **1,785** (1,783–1,804) | 464 ms | 583 (582–587) | 243 ms |

- 单位池吞吐随连接数单调上升，但边际收益递减（8→16 +33%，16→32 +16%，32→64 +13%），P99 在 64 连接时明显变差；MySQL 容器 CPU 从 111% 升到 164%，`Threads_running` 从 5 升到 45。下一个限制已转到 MySQL / 主机一侧（与应用、k6 同机，未能隔离）。
- 单计数器从 16 到 64 连接吞吐不变，`Threads_running` 从 16 升到 58，每条 SQL 平均耗时从 6.3 ms 升到 26.7 ms——多出的连接全部在同一行锁前排队。**给热点计数器加连接只会加长队列。**
- 每次成功预留的行锁等待：单位池 0.016–0.035 次，单计数器 1.0 次；死锁、锁超时均为 0。

## E8：多应用实例（单热点，只预留，150 并发，每实例 16 连接）

| 实例数 | 单位池 成功/s | 单位池 P99 | 单计数器 成功/s | 单计数器 P99 |
| --- | --- | --- | --- | --- |
| 1 | 1,356 (1,083–1,376) | 352 ms | 586 (509–586) | 330 ms |
| 2 | 1,505 (1,487–1,509) | 405 ms | 561 (560–562) | 344 ms |
| 3 | 1,520 (1,482–1,565) | 512 ms | 540 (537–555) | 359 ms |

- 每个实例都运行自己的后台补充与到期任务，k6 的确认 / 取消故意发往另一个实例。所有运行审计通过，死锁 0。
- 单位池 1→2 实例 +11%，3 实例持平：总连接数从 16 增到 48，但 MySQL CPU 停在约 154%，同机的多个 JVM 与 k6 先耗尽了主机。与 E7 的 64 连接单实例（1,785/s）相比，多实例反而更低，说明此时多出的 JVM 本身就是开销。
- 单计数器随实例增多略降（586 → 540）：更多进程争同一行。

## E9：进程崩溃与重启

两个实例跑 90 秒完整生命周期（70% 确认、20% 取消、10% 到期，TTL 10 秒），第 30 秒对 8081 实例 `kill -9`，第 56.6 秒重启完成。客户端遇到网络错误或 5xx 时，用**同一个幂等键 / 支付引用**换到下一个实例重试（`benchmarks/k6/crash-lifecycle.js`）。

| 指标 | 结果 |
| --- | --- |
| 迭代 / 客户端最终确认成功的预留 | 57,264 / 57,264 |
| 数据库中的预留数 − 客户端确认成功数 | **0** |
| 首次成功 / 换实例重试后创建 / 重试得到幂等重放（已提交但响应丢失） | 54,248 / 3,012 / **4** |
| 换实例重试次数（宕机 26 秒内） | 6,009 |
| 最终失败的预留 / 确认 / 取消 | 0 / 0 / 0 |
| CLAIMED / CANCELLED / EXPIRED | 40,099 / 11,508 / 5,657（与客户端计数一致） |
| 已过期仍为 ACTIVE、孤儿头 / 明细 / 单位 | 0 / 0 / 0 / 0 |
| 不变量审计 | 全部通过 |

被杀进程中未提交的事务由 InnoDB 回滚；它持有的行锁在 1–4 秒内释放（另行实测：经 colima 端口转发的连接在客户端被 `kill -9` 后，MySQL 侧事务 1–4 秒内消失）。

**一次被纠正的误判**：第一次演练中有 25 次确认 / 取消以 409 `RESERVATION_EXPIRED` 失败，追踪显示它们的第一次尝试“挂起”约 24 秒。根因是演练脚本：k6 的输出接在管道上而脚本在重启完成后才读取，宕机瞬间约 350 条失败日志写满了 64 KB 管道缓冲，写日志的 VU 全部被阻塞，醒来时 10 秒 TTL 已过。改为把 k6 输出写入文件后重跑，上表为重跑结果。被阻塞的 VU 也掩盖了真实的切换压力：修正后宕机期间的换实例重试从 357 次变为 6,009 次，全部成功。

## E10：经 ProxySQL 的连接归因

应用经 ProxySQL 2.7.3 连接 MySQL（`compose --profile proxysql`），SQL 中的 `/* conn_tag:… */` 注释由 `query_digests_keep_comment` 保留在摘要中。测量窗口内约每 100 ms 采样一次代理的会话表，持有后端连接的会话按正在执行的语句（事务内空闲时按该会话最近一次的语句）归到业务标签，得到“代理后端占用”的估算。

### 发现：默认设置下代理无法复用后端连接

第一轮（[raw/…/proxysql-pinned](raw/2026-10-16-drills/proxysql-pinned)）中，所有配置下后端连接使用都恒为 16（= 客户端连接数）。会话扩展信息显示 `MultiplexDisabled = true`：Connector/J 建连时执行的 `SELECT @@session.…` 让 ProxySQL 永久禁用了该连接的复用。此时代理只是直通，“代理后端占用”就是客户端连接的生命周期，按标签归因也失去意义。在 [`scripts/proxysql/proxysql.cnf.template`](../../scripts/proxysql/proxysql.cnf.template) 中加入 `match_pattern="@@", multiplex=2` 的查询规则后，空闲时持有后端的会话从 16 降到 1。

### 复用正常时的结果

| 配置 | 成功预留/s | 注入调用 应用侧连接占用 | 注入调用 代理后端占用 | reserve 应用侧 / 代理后端占用 | 后端连接 平均 / 峰值 |
| --- | --- | --- | --- | --- | --- |
| 只预留（10 商品，50 并发） | 1,231 (1,229–1,240) | — | — | 16.1 / 12.1 s/s | 12.4 / 16 |
| + 事务外等待 100 ms × 16 | 1,219 (1,216–1,227) | 0 | 0 | 15.9 / 12.4 s/s | 12.2 / 16 |
| + 持有连接不执行 SQL 100 ms × 16 | **709** (709–719) | **10.4 s/s** | **0.00 s/s** | 5.6 / 4.6 s/s | **4.6** / 13 |

- 注入调用把应用侧连接池占满，预留吞吐降 42%、连接获取等待从 27 ms 升到 62 ms；但它不执行 SQL、不开事务，ProxySQL 根本不会给它分配后端连接，**在代理侧的占用为 0**，后端连接反而空闲（平均 4.6 个）。
- 也就是说：代理侧归因只能看到“在事务中或在执行 SQL 时”的占用；“借了连接却什么都不做”的调用只能从应用侧（Hikari，按业务标签）看出来。文章用 ProxySQL 定位到问题，前提是那些调用在事务中持有连接。这也是设计文档第 12 节“应用 Hikari 持有时间不等于 ProxySQL 后端占用”的实测。
- 只预留时，代理后端占用（12.1 s/s）低于应用侧（16.1 s/s）：复用让事务之外的连接持有不再占后端。经代理的吞吐与直连同量级；本次没有设计直连 / 代理的严格对照，不对代理开销下结论。

## E11：Redis → MySQL 影子迁移演练

设计见[总体技术方案第 15 节](../../docs/总体技术方案.md#15-redis--mysql-影子迁移实验)，接口见[接口契约第 13 节](../../docs/接口契约.md#13-迁移实验接口仅-migration-profile)。两个应用实例（模式存于 Redis，两实例共享），90 秒完整生命周期（TTL 10 秒），确认 / 取消发往另一个实例。时间表：0–30 秒 `REDIS_PRIMARY`（Redis 为事实来源，MySQL 影子）→ 30–60 秒 `MYSQL_PRIMARY`（切换，Redis 双写）→ 60–75 秒回切 `REDIS_PRIMARY`（演练回切开关）→ 75–90 秒 `MYSQL_PRIMARY`。

| 指标 | 结果 |
| --- | --- |
| 预留 / 确认 / 取消 | 58,554 / 41,014 / 11,711，**全部成功** |
| 影子比对（各阶段合计） | 全部 `match`，**0 处不一致** |
| 跨切换的在途预留 | 在一个系统为主时创建、在另一个系统为主时确认 / 取消，全部成功 |
| 静止后收敛 | ≤ 73 秒后两系统完全一致：10 个维度可售量相等，CLAIMED 41,014 / CANCELLED 11,711 / EXPIRED 5,829 两边相同 |
| MySQL 不变量审计 | 通过 |

- 切换后的阶段里有少量请求仍由切换前的系统处理（三次切换后分别为 12 / 56 / 14 次，占该阶段 0.03%–0.3%）：请求在读取模式之后、执行之前遇到切换，属预期；它们的影子比对同样全部一致。
- **收敛需要时间**：负载停止 22 秒时 MySQL 仍有 3,007 个、Redis 有 1,894 个 ACTIVE（其中 MySQL 806 个已过期未清理），73 秒内全部清理完毕。两边的到期清理在高负载下都会积压；MySQL 的到期任务每个候选开一个短事务并与确认 / 取消争同一批热点账本行，两个实例会扫描到相同候选（由头锁保证只释放一次），因此加实例并不加快清理。这是设计 7.8 节中“多实例扫描相同 ID”的代价，生产中需监控 `stockhold_expiry_lag_seconds`。（已于 2026-10-18 改为 SKIP LOCKED 批量领取，见[修复报告](2026-10-18-fixes.md)。）一致性检查本身要 SCAN 约 5.8 万个 Redis 键、单次约 20 秒，因此 73 秒是上限。
- 第一次演练在负载停止 18 秒后立刻比较，因上述积压判为不一致（两边 ACTIVE / EXPIRED 合计相等、CLAIMED / CANCELLED 完全相同）；演练已改为轮询直到收敛或超时，上表为重跑结果。
- 影子比对能抓到真实分歧：单元测试 `shadowDivergenceIsRecordedAndReportedNotHidden` 构造了旧系统账面多于 MySQL 的漂移，事实来源成功、影子库存不足被记录为不一致，一致性检查报告不一致。本次演练两边账面一致，因此没有出现。

## 局限

- 独立数据库服务器未做（需要另一台机器）；E7 / E8 的上限受同机资源限制。
- E10 的代理后端占用是 100 ms 采样估算，事务内空闲时按会话最近一次语句归因。
- E11 的旧系统是按文章描述构造的模拟（见设计 15.4），不实现分歧的自动修复。
- 演练（E9、E11）各运行 1 次；E7、E8、E10 每个配置 3 次。
