# 2026-10-15 单位池 vs 单计数器：单机压测

**一句话结论**：在同一台笔记本上，单热点只预留的场景下，单位池 + `SKIP LOCKED` 的成功预留吞吐约为单计数器的 2.1 倍；单计数器几乎每次预留都要等行锁，单位池只有约 2%。记录在案的 60 次运行（E1–E5 共 42 次，E6 共 18 次）全部通过不变量审计：没有超卖、没有少卖、没有死锁、没有把锁竞争误报成售罄。另有 1 次运行因压测执行器清库的缺陷被剔除并整组重跑，见“正确性”。这是单机的相对比较，**不是**生产容量结论。

## 环境

- 主机：Apple M1 Max（10 核）、64 GiB、macOS 15.8。**应用、k6 与 MySQL 在同一台机器上**，相互争用 CPU。
- MySQL：8.4.11，运行在 colima 虚拟机（4 vCPU / 8 GiB，Ubuntu 24.04）的 compose 容器中；`READ-COMMITTED`、`innodb_lock_wait_timeout=1`、`innodb_thread_concurrency=0`、`max_connections=300`、`innodb_buffer_pool_size=128MiB`（默认值，未调优）。
- 应用：Zulu OpenJDK 21.0.8；Hikari 最大 16 连接；HTTP 线程 200；`dev,benchmark` profile（`stockhold.reserve.max-concurrent=256`）。
- 压测：k6 v2.3.0。
- 代码：E1–E5 为 commit `9a6b343`（工作区仅 k6 脚本增加了按操作的子指标，业务代码未改）；E6 为 `7275e1b`。原始数据见 [raw/2026-10-15](raw/2026-10-15) 与 [raw/2026-10-16-connection-optimization](raw/2026-10-16-connection-optimization)，`environment.json` 记录了上述参数。

## 方法

用 [`benchmarks/run_matrix.py`](../run_matrix.py) 执行，[`benchmarks/summarize.py`](../summarize.py) 汇总，可完整复现：

```bash
docker compose up -d && ./mvnw -DskipTests package
python3 benchmarks/run_matrix.py --out benchmarks/reports/raw/<日期> --reps 3 --warmup 10s --duration 60s
python3 benchmarks/summarize.py benchmarks/reports/raw/<日期>
```

- 每组实验启动一个新的应用进程；每次运行前清空库存相关表、重新播种（每维度 H = 10,000,000），并在播种后立即审计，起点不干净就中止。
- 每次运行：10 秒预热（不计入）→ 60 秒固定并发的测量窗口 → 不变量审计。指标取测量窗口前后的差值；约每 2 秒采样一次 Hikari pending、MySQL `Threads_running` 与容器 CPU。
- 每个配置重复 3 次。表中数值为**中位数（最小–最大）**。
- **相对计划的降级**：计划 6.4 要求 30 秒预热 + 120 秒测量；本次为 10 秒 + 60 秒，且只覆盖了下面 6 组实验，未跑完整的 6.2 矩阵（Hikari 8/32/64、购物车 20 维度、单维度数量 5/50、倾斜分布等）。
- 库存从未在测量窗口内耗尽：只预留的运行结束时 R 最多约 8.3 万件，远小于 H，没有“售罄后快速返回 409”造成的虚高吞吐。
- 同一配置跨批次的差异约 5%：E1 `pool-vus50`（1,128/s）与 E5 `capacity1000-vus50`（1,072/s）配置相同。小于这个幅度的差异不作结论。

## 结论

### 1. 文章的核心论点成立：热点从“抢一行”变成“领不同行”

E1 单热点下，单位池在 50 / 200 并发时稳定在约 **1,128 次/秒**，单计数器约 **526 次/秒**。MySQL 侧的证据最直接：单计数器每次成功预留平均有 **1.0 次**行锁等待（约 24 ms），单位池只有 **0.02 次**。单位池的这部分锁等待来自同步补充争用账本行，不来自领取单位。

### 2. 单位池的下一个瓶颈是连接，而不是 MySQL

单位池在 50 和 200 并发下吞吐相同，此时 16 个连接全程被占满（每秒连接占用约 16 秒），Hikari pending 约 31 / 173，而 MySQL 容器 CPU 约 145%（虚拟机共 400%）。每次预留借了 **3 次**连接，其中两次是事务外的只读查询（幂等预查、池容量校验）。E6 按文章的思路把它降到 1 次，结果见下一节。

### 3. 完整生命周期下优势明显缩小（E2）

10 热点完整生命周期中，单位池只领先约 10%（624 vs 569 次/秒），预留 P99 反而更高（133 vs 111 ms）。确认、取消、过期仍要串行更新账本行（单位池每次成功预留对应 0.31 次行锁等待），同步补充也要争用这一行。这与设计文档 4.3 节的预判一致：**单位池只拆散了预留这一步的竞争，账本行仍是确认 / 释放路径上的热点**。

### 4. UNION ALL 有效（E3）

5 维度购物车下，`UNION ALL` 比逐维度 `SELECT` 吞吐高约 16%（671 vs 579 次/秒），P99 从 272 ms 降到 205 ms，减少了每次预留的往返次数。锁形态与逐维度路径相同（见 `UnionAllReserveLockShapeTest`）。

### 5. 复现了文章的连接瓶颈现象（E4）

注入“拿着连接 100 ms 不执行 SQL”的调用后，预留吞吐从 1,177 降到 537 次/秒，而 **MySQL CPU 从 142% 降到 87%**，`Threads_running` 从 9.8 降到 3.3：数据库更闲，吞吐却减半。预留自身的 SQL 时间并未变长（0.58 ms），变长的是等连接（9.5 → 28.3 ms）。按业务标签归因能直接指出占用者：注入调用每秒占用约 11.9 秒连接时间，与等长的事务外等待（约 0）形成对照。

### 6. 池容量不能太小（E5）

容量 50 时吞吐比容量 1,000 低约 23%（824 vs 1,072 次/秒），P99 从 169 ms 升到 247 ms。原因是池很快被领空：池缺行从每秒约 23 次升到约 137 次，同步补充随之频繁争用账本行（每次成功预留的行锁等待从 0.02 次升到 0.15 次）。这印证了文章把池容量定在 1,000 的考量：要给突发留足余量。

### 7. 正确性

所有被记录的运行（E1–E6）审计全部通过：每个维度 H ≥ A ≥ 0、A = P + R、P ≤ 容量，H = 初始库存 − 已确认数量；单计数器的 R 与 ACTIVE 明细一致。409 误报售罄、503 繁忙、429 限流、未归类错误均为 0；MySQL 死锁与锁等待超时计数均为 0。

**一次被剔除的运行**：最初的 E4 `hold-outside` 第 2 次运行审计失败，两个维度的 A = P + R 恰好差 1,000。已复现其成因：执行器逐张 `TRUNCATE` 时先清了单位表，应用的后台补充任务在两次 `TRUNCATE` 之间按尚未清掉的旧账本把池补满，留下 1,000 个孤儿单位。这是执行器绕过协议直接删表造成的，不是预留协议的问题，正常业务不会删除单位行。执行器已改为先清账本、并在播种后立即审计，整组 E4 用同一份 jar 重跑，上表为重跑结果。这次失败也说明审计确实能抓到 A = P + R 的破坏。

## 连接优化：每次预留只借 1 次连接（E6）

E1 显示单位池卡在 16 个连接上。commit `7275e1b` 去掉了事务外的两次借出：池容量创建后不可修改，因此在进程内缓存；幂等预查改为依赖预留事务第一条语句（插入头）上的唯一约束，失败路径仍先按重放 / 冲突处理（`IdempotencyAndStateIntegrationTest` 固定了这个优先级）。为保证公平，单计数器同样去掉了幂等预查。

| 并发 | 单位池 优化前 | 单位池 优化后 | 单计数器 优化前 | 单计数器 优化后 | 单位池每次预留借出连接 |
| --- | --- | --- | --- | --- | --- |
| 10 | 935 (889–942) | **1,096** (1,092–1,099) | 499 (487–513) | 523 (523–530) | 3.02 → 1.02 |
| 50 | 1,128 (1,122–1,128) | **1,240** (1,194–1,302) | 526 (523–527) | 507 (484–533) | 3.02 → 1.03 |
| 200 | 1,128 (1,127–1,133) | **1,290** (1,118–1,292) | 522 (521–524) | 540 (537–541) | 3.02 → 1.02 |

- 单位池吞吐提高 10%–17%，高于约 5% 的批次波动，但 200 并发这组 3 次之间的范围较宽。50 / 200 并发下 P95 分别从 94 / 425 ms 降到 76 / 302 ms；P99 方向不一致：50 并发从 149 升到 170 ms，200 并发从 595 降到 471 ms。
- 单计数器几乎不变：它的上限由那一把行锁决定，少借连接没有用。这个对照说明两种方案的瓶颈性质不同。
- 优化后单位池与单计数器的差距从约 2.1 倍扩大到约 2.4 倍。
- 优化后单位池仍占满 16 个连接，每次借出平均持有约 11.7 ms（16 连接 ÷ 11.7 ms ≈ 1,370 次/秒的理论上限，与实测接近）。**推测**下一个限制是事务内每条语句到虚拟机里 MySQL 的网络往返；本次没有做验证它的实验（例如加大 Hikari 连接数或在宿主机上直接运行 MySQL）。

## 局限

- 单机、同机压测：k6、应用与 MySQL 争用同一颗 CPU；MySQL 在虚拟机里且 buffer pool 为默认 128 MiB。绝对数值不能外推到生产，也不能与任何大型电商的峰值比较。
- 单个应用实例、16 连接；未做多实例、多分片。
- 每次运行 60 秒、3 次重复；未覆盖计划中的完整矩阵（见“方法”）。
- 未使用 ProxySQL，连接归因只来自应用侧 Hikari 指标。
